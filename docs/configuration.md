# Configuration

- **`Directory.Build.props`** (solution root) forces every project's build output into a single shared folder, `Accounts\bin\Debug\` — see [Solution Structure](overview.md#solution-structure).
- **`app.config`** files (found in `Accounts`, `connectionit`, `AccountModelsLib`, and likely others not individually enumerated) carry `<connectionStrings>` and legacy `<entityFramework>`/assembly-binding-redirect sections (EF6-era config alongside the modern EF Core code path — a leftover from an earlier EF version, not necessarily still exercised).
- **The intended production configuration mechanism is an encrypted XML file**, not `app.config`: `ConnConfigInfoXML` reads/writes `CommonFiles\ConnInfo.xml` next to the running EXE, containing server/database/credentials plus date-format/calendar settings, "obfuscated" via the custom Caesar-cipher `EncryptProcess` class (see [Database Access](database.md#database-access) — this is not real encryption). The `DBConfig` form (present near-identically in `AccountCommonDataLIB`, `connectionit\Alter_DataBase`, and standalone in `DataBaseSettining`) is the UI for editing this file.
- **A large amount of additional runtime configuration lives in database tables rather than files**: `SysConfig`/`SysConfigMenus` (feature/menu flags), `PERMATIONS`/`FORMS_DETAILES`/`PROJECT_DETAILES` (per-user permissions), `USER_DETAILES` (accounts). These are read into the static `Common` class at startup and/or queried live by permission-gated menu code.
- **Feature/vertical selection is also driven by static flags set in `Program.cs`** at startup (e.g. `AccountCommonDataLIB.Common.Project_ID = 2; Common.Project_Module_Str = "Account Module";`, `Common.PointOfSale`) — the same compiled binaries appear to serve multiple business verticals/deployments by branching on these values, rather than having separate builds per vertical (not fully confirmed — see [Areas Requiring Further Investigation](investigations.md)).
- **Licensing/hardware-lock configuration**: `HardWareInfo.CheckSerials_Compatibility()` is called at startup in the main ERP shells to validate the app is running on an authorized machine; separate, unrelated **hardcoded hard-stop expiry dates** exist in at least two places (`GHospital_Care\Program.cs`: `2024-08-25`; `Alter_DataBase\Program.cs`/`LOGINFRM`: `2018-01-01`..`2027-06-06` window) — these are build-time constants, not configuration a user can change through any UI found.
