# Database

- **Type:** Microsoft SQL Server (confirmed throughout via `Microsoft.Data.SqlClient`/`SqlConnection` and `UseSqlServer(...)` in EF Core configuration). One `Alter_DataBase` sub-form (`SysConfig\ConfigForm.cs`, "Snowflake Configuration Settings") and one (`SQLLiteConfig\ConfigFormSqlLite.cs`, SQLite) reference other database technologies but **have no callers found anywhere in the project** — treat as dead/experimental code, not evidence of multi-database support.
- **Canonical schema reference:** `ERP_V1_3.md` at the solution root is an existing, extremely detailed (490KB) AI-oriented reference documenting hundreds of actual tables grouped into 14 module sections (`01` general accounts/GL, `02` car maintenance, `03` invoices/tax, `04` reservations/appointments, `05` items/inventory, `06` warehouses/purchasing, `07` HR/payroll, `08` banks/treasury, `09` production/textile, `10` construction/real-estate, `11` tourism, `12` system/users/permissions, `13` lookup tables, `14` misc/support tables), plus consolidated business rules (multi-branch via `Branch_Id`, multi-currency via `Equivalent_*` fields and `Factor`, trial-balance balancing handled in application code rather than extra DB entries, inventory valuation via weighted-average cost, GRIR/PPV supplier-invoice matching, COGS/WIP for production). **Treat `ERP_V1_3.md` as the source of truth for schema/business-rule questions** rather than re-deriving them from form code — it already encodes rules like "never assume `Id` is a PK without checking DDL" and "never rename/merge `Temp`/`BACK`/`History` tables."
- **Quick entity → table map** (from `ERP_V1_3.md` §15, reproduced here for convenience): Branches→`Account_Branches`, Currencies→`Currency`, Main accounts→`MainAccount`/`Main_Accounts`, Sub-accounts→`Submain_Account`, Journal entries→`Account_Entry_List`/`Account_Entry_Details`, Customers→`Customer`, Suppliers→`Supplier`, Employees→`Employee`, Items/services→`Item`, Stores→`Store`, Units→`Unit_item`/`unit`, Purchase/sales bills→`Bills_List`/`Bills_Details`, Invoices→`Invoices_List`/`Invoices_Details`, Cars→`Cars`, Car work orders→`CarsWorkOrders`, Reservations/appointments→`Appointments`/`AppointmentSessions`/`AppointmentPackages`, Banks→`Banks`, Cash boxes→`Money_Transaction_Box`, Financial periods→`Financial_Period`, Cost centers→`Cost_Center_Tree`, Tax invoices→`TaxInvoices_List`, Users/auth→`Authentication`/`USER_DETAILES`, Settings→`SysConfig`.
- **Known schema-quality issues** (per `ERP_V1_3.md` §12, and independently confirmed by the forms-inventory passes in `FORMS_INVENTORY.md`): inconsistent historical naming (`Item`/`Items`, `Lookup`/`LookUp`), spelling/transliteration artifacts baked permanently into table/column names (`Purshing`, `Detailes`), legacy `image`-typed columns, and a large set of recurring audit columns (`User_Id`, `OperationDate`, `Insert_ServerDateTime`, `Update_ServerDateTime`, `Edit_User_Id`, `ProcessNo`). **Do not "fix" these names** — `ERP_V1_3.md` explicitly mandates that generated C# model classes and properties match SQL table/column names *verbatim*, typos and all, unless a rename is explicitly requested.
- **Connection strings are hardcoded directly in source in multiple places**, not centralized in one config file:
  - `AccountModelsLib\Common\operations.cs`, method `ReturnConnStr()`, contains a long history of overwritten `conn_str_ = "..."` assignments (C# keeps only the *last* one); the currently-active one uses `Integrated Security=SSPI` (no embedded password) pointed at a specific named SQL Server instance. Above it in the same method are many now-dead, commented/overwritten assignments — **several of which contain plaintext `sa`-user passwords and internal server IPs for past client deployments**. Values are intentionally not reproduced in this document; if this code is ever touched, treat every line in that method as potentially sensitive and scrub/rotate rather than assume it's inert.
  - `Accounts\app.config` / other `app.config` files also carry `<connectionStrings>` entries (mostly `Integrated Security=True`, no embedded password, but naming real internal server instances).
  - `Alter_DataBase\DBConfig.cs` (in `connectionit`) and `Alter_DataBase\BackupDB_CLS.cs`/`BackupFrm.cs` were separately flagged by the forms-inventory pass as containing additional hardcoded/commented `sa`-user connection strings for backup/restore operations. Not reproduced here.
  - A separate, XML-file-based configuration path also exists and appears to be the intended *production* mechanism (see [Database Access](#database-access) and [Configuration](configuration.md) below) — the hardcoded strings in `operations.cs` function as a fallback/default when `Common.IS_ReadConStrFromXMLInfo` is not set to read from XML.
- **No evidence found of more than one *simultaneous* production database** — the multiple hardcoded connection strings represent **historical per-client/per-environment values left in place over time**, not active multi-tenancy. Confirm with the team before assuming otherwise.

## Database Access

- **Core DAL class:** `AccountModelsLib.operations` (in `AccountModelsLib\Common\operations.cs`, ~1600 lines) is the base data-access class almost the entire solution ultimately builds on. It is subclassed by `AccountCommonDataLIB.operations`, which most Form-level code actually instantiates (`new operations(...)` / `new AccountModelsLib.operations()`).
- **Hybrid ADO.NET + EF Core in the same class:** `operations` simultaneously exposes:
  - Raw ADO.NET fields — `public SqlConnection conn`, `SqlCommand cmd`, `SqlDataAdapter ada`, `SqlCommandBuilder combd`, `SqlDataReader dr`, `SqlTransaction tns` — with helper methods like `return_dataset(sql)`, `return_DataTable(sql)`, `insert_me(sql)`, `update_me(sql)`, `delete_me(sql)`, `insert_me_SP(...)` that take a **whole SQL string built by the caller** and execute it directly.
  - An EF Core context — `public My_DbContext db` (`AccountModelsLib\Common\MyDbContext.cs`), exposing **145 `DbSet<>` properties**, configured via `UseSqlServer(ConnStr)` with `.EnableDetailedErrors()` **and `.EnableSensitiveDataLogging()`** (the latter logs actual parameter values — a data-exposure risk if this ever runs against production logs; see [Known Technical Constraints](known-constraints.md)).
  - Transaction support that spans both: `BeginTransaction()` opens a `SqlTransaction` on the raw connection *and* calls `db.Database.UseTransaction(tns)` so the same transaction covers both access styles; `Commit()`/`Rollback()` close it out.
- **Dominant pattern in practice, by far, is raw string-built SQL executed through the `operations` helper methods** — every forms-inventory batch in `FORMS_INVENTORY.md` independently confirmed this: SQL strings assembled with plain C# string concatenation (e.g. `"Update Money_Transaction_Box Set Bank_Balance=" + Bank_Balance + " where id=" + id`) and passed to `insert_me`/`update_me`/`return_DataTable`. **No parameterized-query usage was found in this pattern anywhere** in the many hundreds of files examined — this is a solution-wide SQL-injection-shaped risk, not an isolated issue (see [Known Technical Constraints](known-constraints.md)).
- **EF Core (`opp.db.*` LINQ) usage exists but is a minority pattern**, concentrated in newer-looking code (e.g. a handful of `Accounts` forms — `AccountsCustomerLinkFrm`, `CustomersLinkToAccountsFrm`, `CalendarAppointmentsFrm`, `FrmPackageEditMulti`, `Item_Transaction_TotalyDetails`, `Mezan_Morgaa_ByPeriod` — and roughly 23 of 67 files in `Connection4It` vs. far fewer elsewhere). Several large modules (`ReservationSystemLIB`, `ConstructionLib`, `Stores`, `Alter_DataBase`) show **zero** EF Core usage in their form files.
- **A parallel legacy typed-`DataSet`/`TableAdapter` pattern** (Visual Studio–generated `.xsd`-backed classes with auto-generated parameterized `SqlDataAdapter` fill methods) is used by many of the RDLC report forms (e.g. in `Reporting_System`, `Store_LIB`, `General_Ledger`'s report forms) — these *are* parameterized by generation, unlike the hand-rolled string-SQL pattern above.
- **Business-logic wrapper classes (`*CLS`/`*Clss`)** sit between most Forms and the DAL — e.g. `AccountEntry_CLS`, `BillsClss`, `TakseetCLS`, `Mezan_MorgaaCLS`, `Requests_Cls`, `CustomerOwnerCLS`, `ProjectsCLS` — meaning a given Form's actual SQL is frequently **not visible in the Form's own file** and lives in a same-folder helper class instead. Several forms bypass this and embed raw SQL directly (documented per-form in `FORMS_INVENTORY.md` where found).
- **Stored procedures** are used, but inconsistently — confirmed real usage inside `GHospital_Care` (dozens of `SP_SAVE_tblXxx`/`SP_GENERATE_XxxID` procs) and scattered elsewhere (`insert_me_SP` helper), but the core ERP modules lean overwhelmingly on inline SQL strings rather than procs.
- **Connection configuration at runtime:** production connection info is intended to come from an **encrypted XML file** (`ConnConfigInfoXML` class, reading `CommonFiles\ConnInfo.xml` next to the EXE), decrypted via a **custom, non-cryptographic Caesar-cipher-style shift cipher** (`EncryptProcess.encrypt`/`decrypt` — adds/subtracts an integer key from each Unicode character; this is *obfuscation*, not real encryption — flagged under [Known Technical Constraints](known-constraints.md)). The `DBConfig` form (re-implemented near-identically in at least three places — `AccountCommonDataLIB`, `connectionit\Alter_DataBase`, and standalone in `DataBaseSettining`) is the UI for editing this XML file. When `Common.IS_ReadConStrFromXMLInfo` is not set to use it, code falls back to the hardcoded strings in `operations.ReturnConnStr()` described above.
- **A separate, apparently-legacy `Connection4It.ConnectionString` class** (`connectionit\UsrCntrl\ConnectionString.cs`) builds an old-style `Provider=SQLOLEDB.1` OLE DB connection string from the same encrypted-XML source — this looks superseded by the SqlConnection-based path above; **not confirmed whether anything still calls it**.
