# Project Overview & Solution Structure

## Project Overview

This repository root contains **many separate, mostly-independent product codebases** that happen to live side by side on disk. This document covers **only the solution defined by `Accounts.sln` / `AccountsNet.sln`** (the two files are functionally identical — see *Solution Structure*), which is a large, long-lived **multi-module Egyptian ERP/accounting system** built on legacy C# WinForms, currently mid-migration from .NET Framework to modern .NET.

The system's core purpose, per its own internal documentation (`ERP_V1_3.md`, a 490KB canonical AI/DB-schema reference already present at the solution root — treat it as authoritative for database schema questions and consult it before writing new SQL/EF code against this database) is:

> "نظام ERP متعدد الوحدات، مع تركيز أساسي على المحاسبة والمخزون، إضافة إلى التكامل مع المبيعات والمشتريات والضرائب والفاتورة الإلكترونية وصيانة السيارات والحجوزات والموارد البشرية والبنوك والإنتاج وغيرها."
> (A multi-module ERP system centered on accounting and inventory, integrated with sales, purchasing, taxes, e-invoicing, car maintenance, reservations, HR, banks, production, and more.)

Confirmed business modules present as actual code in this solution: General Ledger / chart of accounts / trial balance, multi-branch & multi-currency accounting, inventory & warehouses, sales/purchase invoicing, Egyptian Tax Authority e-invoicing, bank checks, car-service workshop (estimations/work orders), tourism/travel reservations (visas, hotels, flights, land transport, bus, Hajj/Umrah), textile/production rates, construction/real-estate project management, HR attendance, POS/restaurant point-of-sale, and a "beauty center" / medical-imaging appointments module. A vendored third-party Hospital Information System (see `GHospital_Care` below) is also bundled in.

**A parallel, early-stage/prototype Blazor rewrite** (web + Blazor-Hybrid MAUI + a shared Razor component library) exists inside the same solution (`Razors/` folder) and appears to be an in-progress modernization effort, not yet wired into the running application. See [Areas Requiring Further Investigation](investigations.md).

Several other top-level folders in this repo root (`AccountsNew`, the six `Humanresource*` client-specific HR forks, `LawyerProject(LIB)`, `MainSystemSIT`, `MakeLicence`, `PointOfSale`, `ReservationSystem`, `TourismSystem`, `Tours`, `Test`, `TestForms`, `wTest`, `UpdateDb`, `GetHardWareInfo`, `WActivation_Date`, `WBar`, `Production_Process`, `Store_LIB11`, `LS_UI`, `MaterialSkin`, `Managed`, `Backup`, `Backup1`, `Backup2`) are **not referenced by `Accounts.sln`/`AccountsNet.sln`** and are out of scope for this document — they appear to be separate legacy products, per-client forks, or backup snapshots. Not investigated further here.

**Companion document:** [`FORMS_INVENTORY.md`](../FORMS_INVENTORY.md) at the solution root holds the detailed, per-project screen-by-screen catalog (every WinForms form's purpose, key operations, navigation targets, DB tables/procs, and per-project "batch observations") plus the full screen-navigation map. This document (`CLAUDE.md`) stays focused on structure, architecture, conventions, and rules; consult `FORMS_INVENTORY.md` when you need the specifics of an individual screen.

## Solution Structure

- Two solution files exist at the repo root: **`Accounts.sln`** and **`AccountsNet.sln`**. They reference the **exact same 42 `Project(...)` entries** (40 real projects + 2 solution folders, `Razors` and `UnderProjects`); the only diff between the files is the ordering of a third-party IDE-skin settings block (`VSStyle`/`VSSkinFlatStyles`/etc. under `GlobalSection`), which is cosmetic. Treat them as the same solution under two names — pick either when opening in Visual Studio.
- `Directory.Build.props` at the solution root sets a single shared setting for every project: `OutputPath` is forced to `Accounts\bin\Debug\` (i.e. **all projects build into one shared output folder next to the `Accounts` project**, not their own `bin\Debug` folders).
- Two "solution folder" groupings exist in the `.sln`: **`Razors`** (groups the four Blazor/MAUI projects) and **`UnderProjects`** (contains only `BackUp_Project`).
- The solution mixes **modern SDK-style, multi-targeted projects** (`net10.0-windows` for Debug builds; `net10.0-windows;net48` for Release — i.e. dual-targeting current .NET and .NET Framework 4.8) with a handful of **legacy, non-SDK-style `.csproj` files** still targeting old Framework versions directly: `Clinic`/`ClinicPatient` (`v4.5`), `DataBaseSetting` (`v3.5`), `EASY E-INVOICE` (`v4.8`), `FreeMedical` (`v2.0`), `AbsencePrecenseProj` (`v3.5`), `EncryptionCA` (unversioned legacy). This is an **incremental, in-progress .NET Framework → modern .NET migration** — some projects have crossed over, some have not.
- `GHospital_Care` (folder `HMIS\GHospital Care\`) is a **vendored third-party commercial product**: a hospital/clinic management system from vendor "GSoft" (see links to `gsoft-bd.com` in its `Help\Register.cs` and `Session\Login.cs`), grafted together with a copy of this ERP's Arabic-language accounting subsystem (`Journal_Entry\`, `Master_Account\` folders inside it use the same `Account_Entry_List`/`Submain_Account`-family tables as the rest of the ERP). Do not assume it follows this solution's own conventions — it has its own English-labeled UI, its own `tblXxx`-style table naming, and its own (apparently disconnected) user table.
- `HMIS\Accounts\` (a nested folder next to `GHospital Care`) is an unrelated vendored/leftover copy of a different solution and was **not investigated** — it is not referenced by `Accounts.sln`.
- `General_Ledger\New folder\General_Ledger\` is a **second, legacy standalone copy** of the General_Ledger app (its own old-style `.csproj`, `TargetFrameworkVersion v3.5`, `OutputType WinExe`, its own `MainFrm.cs`), sitting alongside the current SDK-style `General_Ledger\General_Ledger\` that the solution actually references. Confirmed via diff that the two trees have diverged (different `Submain_Account` column names between versions). Not part of the active build; kept in the tree, presumably as a pre-migration snapshot.
- Several projects contain files physically present on disk but **explicitly excluded from compilation** via `<Compile Remove>` in their `.csproj` (confirmed in `General_Ledger`, `ProductionsRates`, `ConstructionLib`, `CarsSystemLib`) — treat any file under a folder named `New folder`, `NewFolder1`, `1111`, or similar as a strong (but not certain) signal of dead/abandoned code; always check the owning `.csproj` for a `<Compile Remove>` before assuming a file is live.
