# Known Technical Constraints

*Observations only — not tasks to execute in this pass. Ranked roughly by risk/impact.*

- **Solution-wide raw, string-concatenated SQL with no parameterization**, executed via the `operations` DAL's `return_dataset`/`return_DataTable`/`insert_me`/`update_me`/`delete_me` methods, which accept a whole caller-built SQL string. Confirmed in every single forms-inventory batch across all 34 WinForms projects examined (see `FORMS_INVENTORY.md`). This is a SQL-injection-shaped risk anywhere a concatenated value can originate from user input (many values are numeric IDs/enums where the practical risk is lower, but plenty of string inputs — names, search terms — are concatenated the same way). No mitigating input-sanitization layer was found.
- **Multiple hardcoded SQL Server connection strings containing plaintext credentials exist directly in source** (`AccountModelsLib\Common\operations.cs`'s `ReturnConnStr()` method; commented-out strings in `connectionit\Alter_DataBase\DBConfig.cs`, `BackupDB_CLS.cs`, `BackupFrm.cs`). Values are not reproduced anywhere in this document; if any of this code is touched, treat every connection-string literal as a potential leaked credential requiring rotation, not as inert dead code.
- **The credential "encryption" used for the production XML-config path is not real cryptography** — `EncryptProcess` is a Caesar-cipher-style integer shift cipher, trivially reversible. Anything relying on it (stored login credentials, e-invoice portal secrets in `AccountsEInvoicesLIB\BranchesFrm.cs`) should be considered effectively stored in plaintext from a security standpoint.
- **`My_DbContext` is configured with `.EnableSensitiveDataLogging()`** in addition to `.EnableDetailedErrors()` — if EF Core logging is ever wired to a persistent/shared log sink in this configuration, it will write actual query parameter values (which can include the credentials/PII flowing through the app) into logs.
- **No password hashing observed anywhere.** Every login flow examined (`LoginPro.Authentication*`, `GHospital_Care\Session\Login.cs`, `administration\LOGINFRM.cs`) compares plaintext passwords directly against a stored `USER_PASSWORD`/similar column.
- **Pervasive empty/swallowed exception handling** (`catch { }` / `catch (Exception ee) { }` with `ee` unused) — measured at roughly 45% of catch blocks in the `Accounts` project alone. Failures (including DB write failures) can be silently lost rather than surfaced or logged.
- **Two of the solution's own "modernized" .NET 10 executables are effectively non-functional as shipped for their intended new purpose**: `AccountsERPSystemNet10`'s Blazor/DI wiring is built but not called from `Main()` (it still runs the legacy `MainFrm_AccountUpdate`); `Stores\Program.cs`'s active code path has its `Application.Run(MainFrm)` call commented out, meaning that project's compiled EXE currently starts and exits without showing any UI.
- **`GHospital_Care` (the vendored hospital system) has a hardcoded hard-stop expiry check** (`if (DateTime.Now.Date > new DateTime(2024, 8, 25)) Application.Exit();`) — as of any date after 2024-08-25 this project will not run at all without a code change. A separate hardcoded expiry window (`2018-01-01`..`2027-06-06`) gates `Alter_DataBase`'s login as well, and will similarly stop that tool from running after 2027-06-06.
- **Massive, solution-wide code duplication via copy-paste-per-workflow/per-client rather than parameterization or shared components.** Confirmed patterns include: near-identical booking/list/print form quadruplets repeated 6× across travel-product types in `ReservationSystemLIB`; an entire `Work_In` folder mirrored almost 1:1 by `Work_Out` in `Accounts`; numbered "version history" folders (`1Order_Receipt_CashFrm` … `90Sandouk_Transaction`, plus `Cash_MoneyNew\`) in `Account_Common_LIB`; four 1400–2300-line near-duplicate cash-disbursement forms (`New_OrderMoney_SarfNew`/`_SarfNewNew`/`_SarfHospital`/`_SarfCurrencyNew`); three or more copies of `DBConfig`, `Master_Account_Details(2)`, `NewAccount_EntryFRM`, and other core forms across different projects/folders. A bug fix applied to one copy will very likely not propagate to its siblings — always check for parallel/near-duplicate forms (see `FORMS_INVENTORY.md`) before assuming a fix is complete.
- **Dead code is left in the tree rather than removed**, sometimes still wired into menus (calls that do nothing) and sometimes explicitly excluded from compilation via `<Compile Remove>` (confirmed in `General_Ledger`, `ProductionsRates` — its entire `Work_Out` outsourcing feature, 10 files — `ConstructionLib`, `CarsSystemLib`). Folders named `New folder`/`NewFolder1`/`Old`/files suffixed `OLD`/`_` are a strong but not certain signal — always check the owning `.csproj`.
- **Mixed source-file text encoding** (UTF-8 vs. legacy Windows-1256 Arabic, no BOM, sometimes both within the same folder) causes Arabic string literals to render as mojibake (`????`/garbled text) when read with naive UTF-8 tooling. This affects real, in-production Arabic captions and validation messages in multiple projects (`ProductionsRates`, parts of `General_Ledger`'s legacy tree, `Store_LIB`, `AbsencePrecenseProj`, `administration`, `LoginPro`, `ConstructionLib`). Any future automated text processing (including AI-assisted edits) must account for this or risk corrupting Arabic text.
- **Global mutable static state** (`AccountCommonDataLIB.Common`/`AccountModelsLib.Common`, `operations`'s static connection fields) is the primary way configuration and session state propagate through the app — tight coupling to load order (`Common.SetSystemParameters()` must run first) and no isolation between concurrent operations within one process.
- **Hardcoded "magic" business values found in code**, e.g. `ServicesGroupAssignFrm.cs` (`ConstructionLib`) has `long Project_Id = 9;` hardcoded; `General_Ledger`'s `Get_Account_BalanceFRM` calls a method with unexplained numeric literal parameters. Treat any bare numeric ID literal in this codebase as suspect until traced to its meaning.
- **`GHospital_Care` has two apparently disconnected user/auth tables** (`tblUserAccount` managed by its own admin screen vs. `USER_DETAILES` actually used for login) — a real, observed data-integrity risk specific to that vendored module.
- **At least one confirmed copy-paste stored-procedure bug**: `GHospital_Care\Pathology\UrineExamine.cs` saves via `SP_SAVE_tblUltraSonography` (the *Ultrasonography* procedure) while passing urine-exam parameters.
- **Two near-duplicate ERP EXE shells** (`AccountsERPSystem`, `AccountsERPSystemNet10`) ship side by side with near-identical `Main()` methods and both ultimately run the same `MainFrm_AccountUpdate` — unclear which is the actual deployed/supported entry point (see [Areas Requiring Further Investigation](investigations.md)).
- **The Razor/Blazor prototype (`Razors\` group) still contains unremoved template scaffolding** (`Weather.razor`, `Counter.razor`/`Counter2.razor`, multiple `MainLayout*.razor` variants, an `ItemSelectorModal - Copy.razor` file) alongside real-looking pages — its production-readiness is unclear (see [Areas Requiring Further Investigation](investigations.md)).
