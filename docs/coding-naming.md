# Coding & Naming Conventions

## Coding Conventions

Distinguish **Observed Convention** (what the code actually, consistently does — follow it when adding to an existing module) from **Recommendation** (this document's own suggestions — none are given here; per the task, this pass is discovery/documentation only, not a redesign proposal).

**Observed Conventions:**
- **DB connections:** created via `new operations(...)` or a subclass (`AccountCommonDataLIB.operations`), never a bare `new SqlConnection(...)` in Form code (a few exceptions found — flagged per-form in `FORMS_INVENTORY.md` where seen, e.g. some `ConstructionLib` list forms). Connection open/close is handled inside `operations`' methods; callers do not manage `SqlConnection` lifetime directly in the common case.
- **Query execution:** the dominant, solution-wide convention is to build a full SQL string in the caller (often via plain C# string concatenation, sometimes via a same-folder `*CLS` helper) and pass it whole to `operations.return_dataset(sql)` / `return_DataTable(sql)` / `insert_me(sql)` / `update_me(sql)` / `delete_me(sql)`. Parameterized queries are the *exception*, found mainly in VS-generated typed-DataSet/TableAdapter report code and in the newer `SqlServerFullMigrator` class in `Alter_DataBase`.
- **Exception handling:** `try { ... } catch (Exception ee) { MessageBox.Show(ee.Message); }` is the standard shape for surfacing DB/IO errors to the user, in Arabic where the rest of the form is Arabic. A very large fraction of catch blocks (measured at 423 of 933 in the `Accounts` project alone) are instead empty `catch { }` — errors silently swallowed. There is also a centralized DB-backed exception logger, `AccountModelsLib.operations.DataDictionaryLogerException(Exception)`, used in some (not all) top-level entry points (e.g. `Program.cs`'s `Application.Run` try/catch).
- **Opening forms:** direct instantiation, `new SomeForm(args...).Show()` for MDI children (`MdiParent` set by the caller, usually `this` inside a MainFrm) or `.ShowDialog()` for modal dialogs. No form factory/service locator pattern exists.
- **Passing parameters between screens:** almost always via **constructor parameters** on the target form (e.g. `new ItemDataCar(CarsWorkOrdersItemProcessedDetail)`, `new NewOrderWork_FRM(Id, bool)`), occasionally via public properties set before `.ShowDialog()` and read back after (e.g. `PrintOptions`'s selected-columns properties). No message-bus/event-aggregator pattern found.
- **Transactions:** via `operations.BeginTransaction(int)` / `Commit()` / `Rollback()`, which opens both a `SqlTransaction` on the raw connection and calls `db.Database.UseTransaction(tns)` so raw ADO.NET and EF Core share one transaction. Call sites typically wrap a save operation in try/Commit/catch/Rollback.
- **Resources:** binary blobs (item images, company logos, fixed-asset photos) are stored **in the database** as `image`-typed columns and streamed through Forms (`frmNewImage`-family forms across several projects) rather than stored on disk with a path reference.
- **SQL style:** no consistent casing or formatting convention for embedded SQL strings (mixed `SELECT`/`select`, inconsistent aliasing); table/column names always match the database exactly, including historical typos (`Purshing`, `Detailes`) — **per `ERP_V1_3.md`, this must never be "corrected."**
- **File/folder organization within a project:** typically one subfolder per business sub-feature (e.g. `Accounts\Work_In\`, `Accounts\Requests\ItemData\`), with a matching `*CLS` class often colocated in the same folder as its Form(s). Folders literally named `New folder`, `NewFolder1`, `New Folder`, `Old`, or a class name suffixed `OLD`/`_` are a strong (not certain) signal of superseded/dead code — always check the owning `.csproj` for a `<Compile Remove>` before relying on such a file.
- **Configuration:** read at startup into static fields on `Common` (`AccountCommonDataLIB.Common`/`AccountModelsLib.Common`) via `Common.SetSystemParameters()`, then referenced as static properties throughout the app rather than passed as explicit parameters or injected.

## Naming Conventions

**Observed Conventions** (not always applied consistently — treat as the dominant pattern, not a hard rule):
- **Forms:** class name usually ends in `Frm`/`FRM`/`Form` (inconsistent casing) — list/grid screens are typically `<Entity>ListFrm`; add/edit dialogs are typically `Add<Entity>` or `Edit<Entity>`; print-preview screens are typically `<Entity>Print`/`<Entity>PRNT`/`Print<Entity>`.
- **Business-logic wrapper classes:** suffixed `CLS` or `Clss` (e.g. `BillsClss`, `AccountEntry_CLS`, `Requests_Cls`) — casing of the suffix itself is inconsistent.
- **Classes/Methods:** PascalCase is the norm but not universal — camelCase, ALL_CAPS (`ADDNEWUSER`, `LOGINFRM`), and Hungarian-ish prefixes on older files (pre-2010-era non-partial-class forms) all coexist, sometimes in the same file.
- **Controls:** custom control library types are prefixed `My` (`MyButton`, `MyTextBox`, `MyComboBox`, `MyDataGridView`, `MyForm`) — from `Project_ControlLIB`.
- **Database objects:** table/column names are the **literal source of truth** (see [Database](database.md)) — do not normalize casing or spelling when generating C# model code against them; EF Core model class/property names must match table/column names exactly, typos included, per `ERP_V1_3.md`'s explicit rule.
- **Arabic-domain-term transliteration into English identifiers** is a recurring, load-bearing naming convention across multiple modules — recognize these when reading code: `Da2n`=دائن (credit), `Madin`=مدين (debit), `Tar7eel`=ترحيل (posting/carry-forward), `Tarseed`=ترصيد (balance-posting), `Mezan_Morgaa`=ميزان مراجعة (trial balance), `Estlam`=استلام (receiving), `Sarf`=صرف (disbursement), `Tasheel`/`Work_Out`=outsourcing/subcontracting, `Tatreez`=تطريز (embroidery), `Fa7s`=فحص (inspection), `Tashteeb`=تشطيب (finishing), `Matwa`/`Seda`=warp-beam/warp (textile terms), `Wardiat`=ورديات (shifts), `Mortaga3`=مرتجع (returned).
- **Variables:** no enforced convention; Hungarian-style prefixes (`str`, `dt`, `ds`, `cmd`) appear on older ADO.NET-heavy code but are not applied consistently.
