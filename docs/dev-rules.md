# Important Development Rules

Rules a developer or AI agent should follow **if asked to make changes** to this codebase (derived from the observed conventions above plus `ERP_V1_3.md`'s own explicit rules — this section states what to follow, it does not authorize or request any change in this pass):

1. **Do not rename database tables, columns, or the C# model properties that mirror them**, even where they contain obvious typos or inconsistent casing (`Purshing`, `Detailes`, `Item`/`Items`) — per `ERP_V1_3.md`'s Canonical Source-of-Truth rule, the database is the source of truth and naming "fixes" would break the required 1:1 EF Core model mapping.
2. **Never assume `Id` is a primary key or that an `*Id`-suffixed column is a working foreign key** without checking actual DDL/constraints — `ERP_V1_3.md` makes this explicit and the forms-inventory passes found real evidence of inconsistent PK/FK usage across the schema.
3. **Before modifying a form, check for parallel/near-duplicate copies** in other folders or projects (numbered folders, `New folder`, `_New`/`_2`/`Old`/`OLD` suffixes) — given the scale of copy-paste duplication documented above, a fix applied to only one copy is very likely incomplete. `FORMS_INVENTORY.md` documents many known duplicate/near-duplicate pairs.
4. **Before assuming a file is dead code, check the owning `.csproj` for `<Compile Remove>`** — several modules have substantial excluded-but-present code (notably all of `ProductionsRates\Work_Out\`).
5. **New database access should go through the existing `operations`/`*CLS` layering already used by the surrounding code**, matching whatever pattern the specific project/folder already uses (raw `operations` calls vs. EF Core `My_DbContext` vs. typed DataSet/TableAdapter) rather than introducing a fourth pattern — consistency with the immediate neighborhood matters more than solution-wide uniformity, since none currently exists.
6. **Never write a raw connection string, password, or the values found in `ReturnConnStr()`/`DBConfig.cs`/`BackupDB_CLS.cs` into a new file, commit, log, or document** — treat these as live secrets requiring rotation, not sample data.
7. **Preserve the existing error-handling shape** (`try/catch` + `MessageBox.Show` for user-facing errors, optionally `AccountModelsLib.operations.DataDictionaryLogerException(ex)` for logging) when touching a form that already uses it, rather than introducing a different exception-handling style in the same file.
8. **Treat any file with mismatched Arabic captions (mojibake) as being in a non-UTF-8 encoding** (likely Windows-1256) — read/write it with the correct encoding rather than corrupting the Arabic text further; do not assume all files in a project share one encoding.
9. **When opening a new screen, follow the existing convention**: `new TargetForm(constructorArgs).Show()`/`.ShowDialog()`, passing context via constructor parameters (not globals) where the surrounding code already does so.
10. **Respect the permission system** (`PERMATIONS`/`FORMS_DETAILES`/`USER_DETAILES`-family tables) when adding a new menu item or screen to an existing MDI hub — this is a real, load-bearing access-control mechanism, not decorative.
11. **Invoice tax/type flags (stated by the user; also saved in memory `invoice-tax-flags-semantics`)**: `IsInvoiceTaxInfo = 1` marks a tax invoice. `Is_Tax_Per_Item = 1` means tax is computed per item, `0` means on the invoice total; with per-item tax, never apply tax again on the invoice total and never add a discount on the total after the per-item tax. **`Invoice_Type` must NOT be used as a tax/non-tax flag** — it is an old flag being eliminated (keep it only as the numbering-series argument of `Make_New_Invoice_No`/`Make_New_Invoice_ReverseNo`). `IsMaintainceInvoice == (int)AccountModelsLib.Models.InvoiceMaintainenceType.maintenance` (=1) means a car-maintenance invoice (`pos` is another member).
12. **Testing any invoice screen must include a stock-balance check (also saved in memory `invoice-test-stock-balance-check`)**: read `Unit_Item.Full_Qua` (large unit) and `Unit_Item.D_Qua` (small unit) for the line's `Unit_Item` row before and after saving. A sales invoice must decrease the balance by the sold quantity; a sales-return invoice must increase it by the returned quantity; a purchase invoice (when built) increases it, a purchase return decreases it. `Unit_Item` links to `Item` via `Item_id`; balances are per store.
