# Project Overview

This repository root contains **many separate, mostly-independent product codebases** that happen to live side by side on disk. This document covers **only the solution defined by `Accounts.sln` / `AccountsNet.sln`** (the two files are functionally identical — see *Solution Structure*), which is a large, long-lived **multi-module Egyptian ERP/accounting system** built on legacy C# WinForms, currently mid-migration from .NET Framework to modern .NET.

The system's core purpose, per its own internal documentation (`ERP_V1_3.md`, a 490KB canonical AI/DB-schema reference already present at the solution root — treat it as authoritative for database schema questions and consult it before writing new SQL/EF code against this database) is:

> "نظام ERP متعدد الوحدات، مع تركيز أساسي على المحاسبة والمخزون، إضافة إلى التكامل مع المبيعات والمشتريات والضرائب والفاتورة الإلكترونية وصيانة السيارات والحجوزات والموارد البشرية والبنوك والإنتاج وغيرها."
> (A multi-module ERP system centered on accounting and inventory, integrated with sales, purchasing, taxes, e-invoicing, car maintenance, reservations, HR, banks, production, and more.)

Confirmed business modules present as actual code in this solution: General Ledger / chart of accounts / trial balance, multi-branch & multi-currency accounting, inventory & warehouses, sales/purchase invoicing, Egyptian Tax Authority e-invoicing, bank checks, car-service workshop (estimations/work orders), tourism/travel reservations (visas, hotels, flights, land transport, bus, Hajj/Umrah), textile/production rates, construction/real-estate project management, HR attendance, POS/restaurant point-of-sale, and a "beauty center" / medical-imaging appointments module. A vendored third-party Hospital Information System (see `GHospital_Care` below) is also bundled in.

**A parallel, early-stage/prototype Blazor rewrite** (web + Blazor-Hybrid MAUI + a shared Razor component library) exists inside the same solution (`Razors/` folder) and appears to be an in-progress modernization effort, not yet wired into the running application. See *Areas Requiring Further Investigation*.

Several other top-level folders in this repo root (`AccountsNew`, the six `Humanresource*` client-specific HR forks, `LawyerProject(LIB)`, `MainSystemSIT`, `MakeLicence`, `PointOfSale`, `ReservationSystem`, `TourismSystem`, `Tours`, `Test`, `TestForms`, `wTest`, `UpdateDb`, `GetHardWareInfo`, `WActivation_Date`, `WBar`, `Production_Process`, `Store_LIB11`, `LS_UI`, `MaterialSkin`, `Managed`, `Backup`, `Backup1`, `Backup2`) are **not referenced by `Accounts.sln`/`AccountsNet.sln`** and are out of scope for this document — they appear to be separate legacy products, per-client forks, or backup snapshots. Not investigated further here.

**Companion document:** [`FORMS_INVENTORY.md`](FORMS_INVENTORY.md) at the solution root holds the detailed, per-project screen-by-screen catalog (every WinForms form's purpose, key operations, navigation targets, DB tables/procs, and per-project "batch observations") plus the full screen-navigation map. This document (`CLAUDE.md`) stays focused on structure, architecture, conventions, and rules; consult `FORMS_INVENTORY.md` when you need the specifics of an individual screen.

## Solution Structure

- Two solution files exist at the repo root: **`Accounts.sln`** and **`AccountsNet.sln`**. They reference the **exact same 42 `Project(...)` entries** (40 real projects + 2 solution folders, `Razors` and `UnderProjects`); the only diff between the files is the ordering of a third-party IDE-skin settings block (`VSStyle`/`VSSkinFlatStyles`/etc. under `GlobalSection`), which is cosmetic. Treat them as the same solution under two names — pick either when opening in Visual Studio.
- `Directory.Build.props` at the solution root sets a single shared setting for every project: `OutputPath` is forced to `Accounts\bin\Debug\` (i.e. **all projects build into one shared output folder next to the `Accounts` project**, not their own `bin\Debug` folders).
- Two "solution folder" groupings exist in the `.sln`: **`Razors`** (groups the four Blazor/MAUI projects) and **`UnderProjects`** (contains only `BackUp_Project`).
- The solution mixes **modern SDK-style, multi-targeted projects** (`net10.0-windows` for Debug builds; `net10.0-windows;net48` for Release — i.e. dual-targeting current .NET and .NET Framework 4.8) with a handful of **legacy, non-SDK-style `.csproj` files** still targeting old Framework versions directly: `Clinic`/`ClinicPatient` (`v4.5`), `DataBaseSetting` (`v3.5`), `EASY E-INVOICE` (`v4.8`), `FreeMedical` (`v2.0`), `AbsencePrecenseProj` (`v3.5`), `EncryptionCA` (unversioned legacy). This is an **incremental, in-progress .NET Framework → modern .NET migration** — some projects have crossed over, some have not.
- `GHospital_Care` (folder `HMIS\GHospital Care\`) is a **vendored third-party commercial product**: a hospital/clinic management system from vendor "GSoft" (see links to `gsoft-bd.com` in its `Help\Register.cs` and `Session\Login.cs`), grafted together with a copy of this ERP's Arabic-language accounting subsystem (`Journal_Entry\`, `Master_Account\` folders inside it use the same `Account_Entry_List`/`Submain_Account`-family tables as the rest of the ERP). Do not assume it follows this solution's own conventions — it has its own English-labeled UI, its own `tblXxx`-style table naming, and its own (apparently disconnected) user table.
- `HMIS\Accounts\` (a nested folder next to `GHospital Care`) is an unrelated vendored/leftover copy of a different solution and was **not investigated** — it is not referenced by `Accounts.sln`.
- `General_Ledger\New folder\General_Ledger\` is a **second, legacy standalone copy** of the General_Ledger app (its own old-style `.csproj`, `TargetFrameworkVersion v3.5`, `OutputType WinExe`, its own `MainFrm.cs`), sitting alongside the current SDK-style `General_Ledger\General_Ledger\` that the solution actually references. Confirmed via diff that the two trees have diverged (different `Submain_Account` column names between versions). Not part of the active build; kept in the tree, presumably as a pre-migration snapshot.
- Several projects contain files physically present on disk but **explicitly excluded from compilation** via `<Compile Remove>` in their `.csproj` (confirmed in `General_Ledger`, `ProductionsRates`, `ConstructionLib`, `CarsSystemLib`) — treat any file under a folder named `New folder`, `NewFolder1`, `1111`, or similar as a strong (but not certain) signal of dead/abandoned code; always check the owning `.csproj` for a `<Compile Remove>` before assuming a file is live.

## Database

- **Type:** Microsoft SQL Server (confirmed throughout via `Microsoft.Data.SqlClient`/`SqlConnection` and `UseSqlServer(...)` in EF Core configuration). One `Alter_DataBase` sub-form (`SysConfig\ConfigForm.cs`, "Snowflake Configuration Settings") and one (`SQLLiteConfig\ConfigFormSqlLite.cs`, SQLite) reference other database technologies but **have no callers found anywhere in the project** — treat as dead/experimental code, not evidence of multi-database support.
- **Canonical schema reference:** `ERP_V1_3.md` at the solution root is an existing, extremely detailed (490KB) AI-oriented reference documenting hundreds of actual tables grouped into 14 module sections (`01` general accounts/GL, `02` car maintenance, `03` invoices/tax, `04` reservations/appointments, `05` items/inventory, `06` warehouses/purchasing, `07` HR/payroll, `08` banks/treasury, `09` production/textile, `10` construction/real-estate, `11` tourism, `12` system/users/permissions, `13` lookup tables, `14` misc/support tables), plus consolidated business rules (multi-branch via `Branch_Id`, multi-currency via `Equivalent_*` fields and `Factor`, trial-balance balancing handled in application code rather than extra DB entries, inventory valuation via weighted-average cost, GRIR/PPV supplier-invoice matching, COGS/WIP for production). **Treat `ERP_V1_3.md` as the source of truth for schema/business-rule questions** rather than re-deriving them from form code — it already encodes rules like "never assume `Id` is a PK without checking DDL" and "never rename/merge `Temp`/`BACK`/`History` tables."
- **Quick entity → table map** (from `ERP_V1_3.md` §15, reproduced here for convenience): Branches→`Account_Branches`, Currencies→`Currency`, Main accounts→`MainAccount`/`Main_Accounts`, Sub-accounts→`Submain_Account`, Journal entries→`Account_Entry_List`/`Account_Entry_Details`, Customers→`Customer`, Suppliers→`Supplier`, Employees→`Employee`, Items/services→`Item`, Stores→`Store`, Units→`Unit_item`/`unit`, Purchase/sales bills→`Bills_List`/`Bills_Details`, Invoices→`Invoices_List`/`Invoices_Details`, Cars→`Cars`, Car work orders→`CarsWorkOrders`, Reservations/appointments→`Appointments`/`AppointmentSessions`/`AppointmentPackages`, Banks→`Banks`, Cash boxes→`Money_Transaction_Box`, Financial periods→`Financial_Period`, Cost centers→`Cost_Center_Tree`, Tax invoices→`TaxInvoices_List`, Users/auth→`Authentication`/`USER_DETAILES`, Settings→`SysConfig`.
- **Known schema-quality issues** (per `ERP_V1_3.md` §12, and independently confirmed by the forms-inventory passes in `FORMS_INVENTORY.md`): inconsistent historical naming (`Item`/`Items`, `Lookup`/`LookUp`), spelling/transliteration artifacts baked permanently into table/column names (`Purshing`, `Detailes`), legacy `image`-typed columns, and a large set of recurring audit columns (`User_Id`, `OperationDate`, `Insert_ServerDateTime`, `Update_ServerDateTime`, `Edit_User_Id`, `ProcessNo`). **Do not "fix" these names** — `ERP_V1_3.md` explicitly mandates that generated C# model classes and properties match SQL table/column names *verbatim*, typos and all, unless a rename is explicitly requested.
- **Connection strings are hardcoded directly in source in multiple places**, not centralized in one config file:
  - `AccountModelsLib\Common\operations.cs`, method `ReturnConnStr()`, contains a long history of overwritten `conn_str_ = "..."` assignments (C# keeps only the *last* one); the currently-active one uses `Integrated Security=SSPI` (no embedded password) pointed at a specific named SQL Server instance. Above it in the same method are many now-dead, commented/overwritten assignments — **several of which contain plaintext `sa`-user passwords and internal server IPs for past client deployments**. Values are intentionally not reproduced in this document; if this code is ever touched, treat every line in that method as potentially sensitive and scrub/rotate rather than assume it's inert.
  - `Accounts\app.config` / other `app.config` files also carry `<connectionStrings>` entries (mostly `Integrated Security=True`, no embedded password, but naming real internal server instances).
  - `Alter_DataBase\DBConfig.cs` (in `connectionit`) and `Alter_DataBase\BackupDB_CLS.cs`/`BackupFrm.cs` were separately flagged by the forms-inventory pass as containing additional hardcoded/commented `sa`-user connection strings for backup/restore operations. Not reproduced here.
  - A separate, XML-file-based configuration path also exists and appears to be the intended *production* mechanism (see *Database Access* and *Configuration* below) — the hardcoded strings in `operations.cs` function as a fallback/default when `Common.IS_ReadConStrFromXMLInfo` is not set to read from XML.
- **No evidence found of more than one *simultaneous* production database** — the multiple hardcoded connection strings represent **historical per-client/per-environment values left in place over time**, not active multi-tenancy. Confirm with the team before assuming otherwise.

## Database Access

- **Core DAL class:** `AccountModelsLib.operations` (in `AccountModelsLib\Common\operations.cs`, ~1600 lines) is the base data-access class almost the entire solution ultimately builds on. It is subclassed by `AccountCommonDataLIB.operations`, which most Form-level code actually instantiates (`new operations(...)` / `new AccountModelsLib.operations()`).
- **Hybrid ADO.NET + EF Core in the same class:** `operations` simultaneously exposes:
  - Raw ADO.NET fields — `public SqlConnection conn`, `SqlCommand cmd`, `SqlDataAdapter ada`, `SqlCommandBuilder combd`, `SqlDataReader dr`, `SqlTransaction tns` — with helper methods like `return_dataset(sql)`, `return_DataTable(sql)`, `insert_me(sql)`, `update_me(sql)`, `delete_me(sql)`, `insert_me_SP(...)` that take a **whole SQL string built by the caller** and execute it directly.
  - An EF Core context — `public My_DbContext db` (`AccountModelsLib\Common\MyDbContext.cs`), exposing **145 `DbSet<>` properties**, configured via `UseSqlServer(ConnStr)` with `.EnableDetailedErrors()` **and `.EnableSensitiveDataLogging()`** (the latter logs actual parameter values — a data-exposure risk if this ever runs against production logs; see *Known Technical Constraints*).
  - Transaction support that spans both: `BeginTransaction()` opens a `SqlTransaction` on the raw connection *and* calls `db.Database.UseTransaction(tns)` so the same transaction covers both access styles; `Commit()`/`Rollback()` close it out.
- **Dominant pattern in practice, by far, is raw string-built SQL executed through the `operations` helper methods** — every forms-inventory batch in `FORMS_INVENTORY.md` independently confirmed this: SQL strings assembled with plain C# string concatenation (e.g. `"Update Money_Transaction_Box Set Bank_Balance=" + Bank_Balance + " where id=" + id`) and passed to `insert_me`/`update_me`/`return_DataTable`. **No parameterized-query usage was found in this pattern anywhere** in the many hundreds of files examined — this is a solution-wide SQL-injection-shaped risk, not an isolated issue (see *Known Technical Constraints*).
- **EF Core (`opp.db.*` LINQ) usage exists but is a minority pattern**, concentrated in newer-looking code (e.g. a handful of `Accounts` forms — `AccountsCustomerLinkFrm`, `CustomersLinkToAccountsFrm`, `CalendarAppointmentsFrm`, `FrmPackageEditMulti`, `Item_Transaction_TotalyDetails`, `Mezan_Morgaa_ByPeriod` — and roughly 23 of 67 files in `Connection4It` vs. far fewer elsewhere). Several large modules (`ReservationSystemLIB`, `ConstructionLib`, `Stores`, `Alter_DataBase`) show **zero** EF Core usage in their form files.
- **A parallel legacy typed-`DataSet`/`TableAdapter` pattern** (Visual Studio–generated `.xsd`-backed classes with auto-generated parameterized `SqlDataAdapter` fill methods) is used by many of the RDLC report forms (e.g. in `Reporting_System`, `Store_LIB`, `General_Ledger`'s report forms) — these *are* parameterized by generation, unlike the hand-rolled string-SQL pattern above.
- **Business-logic wrapper classes (`*CLS`/`*Clss`)** sit between most Forms and the DAL — e.g. `AccountEntry_CLS`, `BillsClss`, `TakseetCLS`, `Mezan_MorgaaCLS`, `Requests_Cls`, `CustomerOwnerCLS`, `ProjectsCLS` — meaning a given Form's actual SQL is frequently **not visible in the Form's own file** and lives in a same-folder helper class instead. Several forms bypass this and embed raw SQL directly (documented per-form in `FORMS_INVENTORY.md` where found).
- **Stored procedures** are used, but inconsistently — confirmed real usage inside `GHospital_Care` (dozens of `SP_SAVE_tblXxx`/`SP_GENERATE_XxxID` procs) and scattered elsewhere (`insert_me_SP` helper), but the core ERP modules lean overwhelmingly on inline SQL strings rather than procs.
- **Connection configuration at runtime:** production connection info is intended to come from an **encrypted XML file** (`ConnConfigInfoXML` class, reading `CommonFiles\ConnInfo.xml` next to the EXE), decrypted via a **custom, non-cryptographic Caesar-cipher-style shift cipher** (`EncryptProcess.encrypt`/`decrypt` — adds/subtracts an integer key from each Unicode character; this is *obfuscation*, not real encryption — flagged under *Known Technical Constraints*). The `DBConfig` form (re-implemented near-identically in at least three places — `AccountCommonDataLIB`, `connectionit\Alter_DataBase`, and standalone in `DataBaseSettining`) is the UI for editing this XML file. When `Common.IS_ReadConStrFromXMLInfo` is not set to use it, code falls back to the hardcoded strings in `operations.ReturnConnStr()` described above.
- **A separate, apparently-legacy `Connection4It.ConnectionString` class** (`connectionit\UsrCntrl\ConnectionString.cs`) builds an old-style `Provider=SQLOLEDB.1` OLE DB connection string from the same encrypted-XML source — this looks superseded by the SqlConnection-based path above; **not confirmed whether anything still calls it**.

## Architecture

- **Not a clean layered architecture.** There is a real, if inconsistently applied, three-tier shape — **Form (UI) → `*CLS`/`*Clss` business-logic wrapper → `operations` DAL (raw ADO.NET and/or EF Core)** — used by the majority of newer/larger modules. But it is routinely broken: many forms (especially older ones, and consistently in `Stores`, `ConstructionLib`, `ReservationSystemLIB`, parts of `Connection4It`, `Account_Common_LIB`, and `Accounts`) embed raw SQL directly in the Form's code-behind, and list forms frequently instantiate `SqlConnection`/`SqlCommand` themselves even when a `*CLS` class exists alongside them. **Do not assume a Repository pattern, Service Layer, or DAL is consistently enforced — verify per-form.**
- **No Dependency Injection** in the WinForms codebase — every dependency is `new`'d up directly in constructors (`new operations()`, `new SomeCLS()`, `new SomeForm()`). The one place DI is used is the **not-yet-active** `AccountsERPSystemNet10` Blazor/`BlazorWebView` wiring (a `ServiceCollection` registering `My_DbContext`, `operations`, `MenuRepository`, etc.) — this is new, unused-at-runtime code, not evidence of a DI pattern elsewhere.
- **Static/global state is pervasive.** `AccountCommonDataLIB.Common : AccountModelsLib.Common` (~800 lines) holds a large amount of static application state — system parameters, feature flags (`Common.PointOfSale`, `Common.Project_ID`, `Common.Project_Module_Str`), version/expiration flags, and more — set once at startup (`Common.SetSystemParameters()`/`GetLoadParameter()` in `Program.cs`) and read from anywhere in the app. `AccountModelsLib.operations` itself also exposes several `public static string` fields (`conn_str_`, `DabaseName`, etc.) shared process-wide. Treat this as a large, implicit, mutable global-state surface — changing it in one place can affect unrelated forms.
- **Shared custom base classes exist but are inconsistently adopted.** `Project_ControlLIB.MyForm : System.Windows.Forms.Form` (RTL, centered start position, Times New Roman) is the closest thing to a "standard base Form" and is used by a large minority of forms in `CarsSystemLib` (majority there), `Account_Common_LIB`, `Connection4It`, `ConstructionLib`, `General_Ledger`, and by the central `MainFrm_AccountUpdate` itself — but the *majority* of forms solution-wide still derive from bare `Form` directly. `Connection4It.Template_Frm` is a second, less-used shared base. **Do not assume a form uses `MyForm`'s behavior unless its declaration says so.**
- **Same-shaped module accreted many times independently.** The travel-booking template in `ReservationSystemLIB` (Booking form + `*CLS` + List form + Print form, repeated 6× for visa/hotel/flight/land/bus/Hajj) and the "numbered version-history folders" pattern in `Account_Common_LIB\Money_Transaction\Cash_Money\` (`1Order_Receipt_CashFrm` … `90Sandouk_Transaction`, plus a further `Cash_MoneyNew\` generation) show the team's historical practice of **cloning a whole feature into a new folder/class name rather than parameterizing or refactoring the original** — expect many "final" versions across the codebase to actually be one of several parallel forks, and check for a "New"/newer-numbered/`_New` sibling before assuming a given form is the one actually in use.
- **Permission-gated dynamic dispatch** (see *Forms Inventory & Screen Navigation*) is a real, load-bearing pattern — `PERMATIONS`/`FORMS_DETAILES`-family tables gate which menu items a user sees and, for some forms with no hardcoded `new X()` call anywhere in their project, appear to be the *only* way those forms get instantiated (likely via reflection using a stored form/class name). This was not fully traced to source in this pass — see *Areas Requiring Further Investigation*.
- **Multiple business verticals share one codebase and one set of infrastructure libraries** (`Connection4It`, `Project_ControlLIB`, `AccountModelsLib`, `LoginPro`) rather than each having its own: accounting/ERP, car-service workshop, construction/real-estate, tourism/reservations, textile production, HR attendance, POS/restaurant, and a "beauty center" module (with an unexplained "X-ray Centers" dashboard) all live in this one solution and reuse the same DAL/UI-control/login infrastructure. `GHospital_Care` is the one outlier that brought its *own* vendored copy of similar infrastructure rather than integrating with the shared one.
- **Two coexisting report-rendering technologies** (Crystal Reports and Microsoft RDLC ReportViewer) are both in active use, sometimes for the same conceptual report in different projects/forms (e.g. `GHospital_Care`'s `PrintServicesItems_HIS.cs` (RDLC) vs `PrintServicesItemsfrm.cs` (Crystal) for the same "print services" concept).

## Coding Conventions

Distinguish **Observed Convention** (what the code actually, consistently does — follow it when adding to an existing module) from **Recommendation** (this document's own suggestions — none are given here; per the task, this pass is discovery/documentation only, not a redesign proposal).

**Observed Conventions:**
- **DB connections:** created via `new operations(...)` or a subclass (`AccountCommonDataLIB.operations`), never a bare `new SqlConnection(...)` in Form code (a few exceptions found — flagged per-form in `FORMS_INVENTORY.md` where seen, e.g. some `ConstructionLib` list forms). Connection open/close is handled inside `operations`' methods; callers do not manage `SqlConnection` lifetime directly in the common case.
- **Query execution:** the dominant, solution-wide convention is to build a full SQL string in the caller (often via plain C# string concatenation, sometimes via a same-folder `*CLS` helper) and pass it whole to `operations.return_dataset(sql)` / `return_DataTable(sql)` / `insert_me(sql)` / `update_me(sql)` / `delete_me(sql)`. Parameterized queries are the *exception*, found mainly in VS-generated typed-DataSet/TableAdapter report code and in the newer `SqlServerFullMigrator` class in `Alter_DataBase`.
- **Exception handling:** `try { ... } catch (Exception ee) { MessageBox.Show(ee.Message); }` is the standard shape for surfacing DB/IO errors to the user, in Arabic where the rest of the form is Arabic. A very large fraction of catch blocks (measured at 423 of 933 in the `Accounts` project alone) are instead empty `catch { }` — errors silently swallowed. There is also a centralized DB-backed exception logger, `AccountModelsLib.operations.DataDictionaryLogerException(Exception)`, used in some (not all) top-level entry points (e.g. `Program.cs`'s `Application.Run` try/catch).
- **Opening forms:** direct instantiation, `new SomeForm(args...).Show()` for MDI children (`MdiParent` set by the caller, usually `this` inside a MainFrm) or `.ShowDialog()` for modal dialogs. No form factory/service locator pattern exists.
- **Passing parameters between screens:** almost always via **constructor parameters** on the target form (e.g. `new ItemDataCar(CarsWorkOrdersItemProcessedDetail)`, `new NewOrderWork_FRM(Id, bool)`), occasionally via public properties set before `.ShowDialog()` and read back after (e.g. `PrintOptions`'s selected-columns properties). No message-bus/event-aggregator pattern found.
- **Transactions:** via `operations.BeginTransaction(int)` / `Commit()` / `Rollback()`, which opens both a `SqlTransaction` on the raw connection and calls `db.Database.UseTransaction(tns)` so raw ADO.NET and EF Core share one transaction. Call sites typically wrap a save operation in try/Commit/catch/Rollback.
- **Resources:** binary blobs (item images, company logos, fixed-asset photos) are stored **in the database** as `image`-typed columns and streamed through Forms (`frmNewImage`-family forms across several projects) rather than stored on disk with a path reference.
- **SQL style:** no consistent casing or formatting convention for embedded SQL strings (mixed `SELECT`/`select`, inconsistent aliasing); table/column names always match the database exactly, including historical typos (`Purshing`, `Detailes`) — **per `ERP_V1_3.md`, this must never be "corrected."**
- **File/folder organization within a project:** typically one subfolder per business sub-feature (e.g. `Accounts\Work_In\`, `Accounts\Requests\ItemData\`), with a matching `*CLS` class often colocated in the same folder as its Form(s). Folders literally named `New folder`, `NewFolder1`, `New Folder`, `Old`, or a class name suffixed `OLD`/`_` are a strong (not certain) signal of superseded/dead code — always check the owning `.csproj` for a `<Compile Remove>` before relying on such a file.
- **Configuration:** read at startup into static fields on `Common` (`AccountCommonDataLIB.Common`/`AccountModelsLib.Common`) via `Common.SetSystemParameters()`, then referenced as static properties throughout the app rather than passed as explicit parameters or injected.

## Naming Conventions

**Observed Conventions** (not always applied consistently — treat as the dominant pattern, not a hard rule):
- **Forms:** class name usually ends in `Frm`/`FRM`/`Form` (inconsistent casing) — list/grid screens are typically `<Entity>ListFrm`; add/edit dialogs are typically `Add<Entity>` or `Edit<Entity>`; print-preview screens are typically `<Entity>Print`/`<Entity>PRNT`/`Print<Entity>`.
- **Business-logic wrapper classes:** suffixed `CLS` or `Clss` (e.g. `BillsClss`, `AccountEntry_CLS`, `Requests_Cls`) — casing of the suffix itself is inconsistent.
- **Classes/Methods:** PascalCase is the norm but not universal — camelCase, ALL_CAPS (`ADDNEWUSER`, `LOGINFRM`), and Hungarian-ish prefixes on older files (pre-2010-era non-partial-class forms) all coexist, sometimes in the same file.
- **Controls:** custom control library types are prefixed `My` (`MyButton`, `MyTextBox`, `MyComboBox`, `MyDataGridView`, `MyForm`) — from `Project_ControlLIB`.
- **Database objects:** table/column names are the **literal source of truth** (see *Database*) — do not normalize casing or spelling when generating C# model code against them; EF Core model class/property names must match table/column names exactly, typos included, per `ERP_V1_3.md`'s explicit rule.
- **Arabic-domain-term transliteration into English identifiers** is a recurring, load-bearing naming convention across multiple modules — recognize these when reading code: `Da2n`=دائن (credit), `Madin`=مدين (debit), `Tar7eel`=ترحيل (posting/carry-forward), `Tarseed`=ترصيد (balance-posting), `Mezan_Morgaa`=ميزان مراجعة (trial balance), `Estlam`=استلام (receiving), `Sarf`=صرف (disbursement), `Tasheel`/`Work_Out`=outsourcing/subcontracting, `Tatreez`=تطريز (embroidery), `Fa7s`=فحص (inspection), `Tashteeb`=تشطيب (finishing), `Matwa`/`Seda`=warp-beam/warp (textile terms), `Wardiat`=ورديات (shifts), `Mortaga3`=مرتجع (returned).
- **Variables:** no enforced convention; Hungarian-style prefixes (`str`, `dt`, `ds`, `cmd`) appear on older ADO.NET-heavy code but are not applied consistently.

## Configuration

- **`Directory.Build.props`** (solution root) forces every project's build output into a single shared folder, `Accounts\bin\Debug\` — see *Solution Structure*.
- **`app.config`** files (found in `Accounts`, `connectionit`, `AccountModelsLib`, and likely others not individually enumerated) carry `<connectionStrings>` and legacy `<entityFramework>`/assembly-binding-redirect sections (EF6-era config alongside the modern EF Core code path — a leftover from an earlier EF version, not necessarily still exercised).
- **The intended production configuration mechanism is an encrypted XML file**, not `app.config`: `ConnConfigInfoXML` reads/writes `CommonFiles\ConnInfo.xml` next to the running EXE, containing server/database/credentials plus date-format/calendar settings, "obfuscated" via the custom Caesar-cipher `EncryptProcess` class (see *Database Access* — this is not real encryption). ## Known Technical Constraints

*Observations only — not tasks to execute in this pass. Ranked roughly by risk/impact.*

- **Solution-wide raw, string-concatenated SQL with no parameterization**, executed via the `operations` DAL's `return_dataset`/`return_DataTable`/`insert_me`/`update_me`/`delete_me` methods, which accept a whole caller-built SQL string. Confirmed in every single forms-inventory batch across all 34 WinForms projects examined (see `FORMS_INVENTORY.md`). This is a SQL-injection-shaped risk anywhere a concatenated value can originate from user input (many values are numeric IDs/enums where the practical risk is lower, but plenty of string inputs — names, search terms — are concatenated the same way). No mitigating input-sanitization layer was found.
- **Multiple hardcoded SQL Server connection strings containing plaintext credentials exist directly in source** (`AccountModelsLib\Common\operations.cs`'s `ReturnConnStr()` method; commented-out strings in `connectionit\Alter_DataBase\DBConfig.cs`, `BackupDB_CLS.cs`, `BackupFrm.cs`). Values are not reproduced anywhere in this document; if any of this code is touched, treat every connection-string literal as a potential leaked credential requiring rotation, not as inert dead code.
- **The credential "encryption" used for the production XML-config path is not real cryptography** — `EncryptProcess` is a Caesar-cipher-style integer shift cipher, trivially reversible. Anything relying on it (stored login credentials, e-invoice portal secrets in `AccountsEInvoicesLIB\BranchesFrm.cs`) should be considered effectively stored in plaintext from a security standpoint.
- **`My_DbContext` is configured with `.EnableSensitiveDataLogging()`** in addition to `.EnableDetailedErrors()` — if EF Core logging is ever wired to a persistent/shared log sink in this configuration, it will write actual query parameter values (which can include the credentials/PII flowing through the app) into logs.
- **No password hashing observed anywhere.** Every login flow examined (`LoginPro.Authentication*`, `GHospital_Care\Session\Login.cs`, `administration\LOGINFRM.cs`) compares plaintext passwords directly against a stored `USER_PASSWORD`/similar column.
- **Pervasive empty/swallowed exception handling** (`catch { }` / `catch (Exception ee) { }` with `ee` unused) — measured at roughly 45% of catch blocks in the `Accounts` project alone. Failures (including DB write failures) can be silently lost rather than surfaced or logged.
- **Two of the solution's own "modernized" .NET 10 executables are effectively non-functional as shipped for their intended new purpose**: `AccountsERPSystemNet10`'s Blazor/DI wiring is built but not called from `Main()` (it still runs the legacy `MainFrm_AccountUpdate`); `Stores\Program.cs`'s active code path has its `Application.Run(MainFrm)` call commented out, meaning that project's compiled EXE currently starts and exits without showing any UI.
- **`GHospital_Care` (the vendored hospital system) has a hardcoded hard-stop expiry check** (`if (DateTime.Now.Date > new DateTime(2024, 8, 25)) Application.Exit();`) — as of any date after 2024-08-25 this project will not run at all without a code change. A separate hardcoded expiry window (`2018-01-01`..`2027-06-06`) gates `Alter_DataBase`'s login as well, and will similarly stop that tool from running after 2027-06-06.
- **Massive, solution-wide code duplication via copy-paste-per-workflow/per-client rather than parameterization or shared components.** Confirmed patterns include: near-identical booking/list/print form quadruplets repeated 6× across travel-product types in `ReservationSystemLIB`; an entire `Work_In` folder mirrored almost 1:1 by `Work_Out` in `Accounts`; numbered "version history" folders (`1Order_Receipt_CashFrm` … `90Sandouk_Transaction`, plus `Cash_MoneyNew\`) in `Account_Common_LIB`; four 1400–2300-line near-duplicate cash-disbursement forms (`New_OrderMoney_SarfNew`/`_SarfNewNew`/`_SarfHospital`/`_SarfCurrencyNew`); three or more copies of `DBConfig`, `Master_Account_Details(2)`, `NewAccount_EntryFRM`, and other core forms across different projects/folders. A bug fix applied to one copy will very likely not propagate to its siblings — always check for parallel/near-duplicate forms (see `FORMS_INVENTORY.md`) before assuming a fix is complete.
- **Dead code is left in the tree rather than removed**, sometimes still wired into menus (calls that do nothing) and sometimes explicitly excluded from compilation via `<Compile Remove>` (confirmed in `General_Ledger`, `ProductionsRates` — its entire `Work_Out` outsourcing feature, 10 files — `ConstructionLib`, `CarsSystemLib`). Folders named `New folder`/`NewFolder1`/`Old`/files suffixed `OLD`/`_` are a strong but not certain signal — always check the owning `.csproj`.
- **Mixed source-file text encoding** (UTF-8 vs. legacy Windows-1256 Arabic, no BOM, sometimes both within the same folder) causes Arabic string literals to render as mojibake (`????`/garbled text) when read with naive UTF-8 tooling. This affects real, in-production Arabic captions and validation messages in multiple projects (`ProductionsRates`, parts of `General_Ledger`'s legacy tree, `Store_LIB`, `AbsencePrecenseProj`, `administration`, `LoginPro`, `ConstructionLib`). Any future automated text processing (including AI-assisted edits) must account for this or risk corrupting Arabic text.
- **Global mutable static state** (`AccountCommonDataLIB.Common`/`AccountModelsLib.Common`, `operations`'s static connection fields) is the primary way configuration and session state propagate through the app — tight coupling to load order (`Common.SetSystemParameters()` must run first) and no isolation between concurrent operations within one process.
- **Hardcoded "magic" business values found in code**, e.g. `ServicesGroupAssignFrm.cs` (`ConstructionLib`) has `long Project_Id = 9;` hardcoded; `General_Ledger`'s `Get_Account_BalanceFRM` calls a method with unexplained numeric literal parameters. Treat any bare numeric ID literal in this codebase as suspect until traced to its meaning.
- **`GHospital_Care` has two apparently disconnected user/auth tables** (`tblUserAccount` managed by its own admin screen vs. `USER_DETAILES` actually used for login) — a real, observed data-integrity risk specific to that vendored module.
- **At least one confirmed copy-paste stored-procedure bug**: `GHospital_Care\Pathology\UrineExamine.cs` saves via `SP_SAVE_tblUltraSonography` (the *Ultrasonography* procedure) while passing urine-exam parameters.
- **Two near-duplicate ERP EXE shells** (`AccountsERPSystem`, `AccountsERPSystemNet10`) ship side by side with near-identical `Main()` methods and both ultimately run the same `MainFrm_AccountUpdate` — unclear which is the actual deployed/supported entry point (see *Areas Requiring Further Investigation*).
- **The Razor/Blazor prototype (`Razors\` group) still contains unremoved template scaffolding** (`Weather.razor`, `Counter.razor`/`Counter2.razor`, multiple `MainLayout*.razor` variants, an `ItemSelectorModal - Copy.razor` file) alongside real-looking pages — its production-readiness is unclear (see *Areas Requiring Further Investigation*).

## Important Development Rules

Rules a developer or AI agent should follow **if asked to make changes** to this codebase (derived from the observed conventions above plus `ERP_V1_3.md`'s own explicit rules — this section states what to follow, it does not authorize or request any change in this pass):

1. **Do not rename database tables, columns, or the C# model properties that mirror them**, even where they contain obvious typos or inconsistent casing (`Purshing`, `Detailes`, `Item`/`Items`) — per `ERP_V1_3.md`'s Canonical Source-of-Truth rule, the database is the source of truth and naming "fixes" would break the required 1:1 EF Core model mapping.
2. **Never assume `Id` is a primary key or that an `*Id`-suffixed column is a working foreign key** without checking actual DDL/constraints — `ERP_V1_3.md` makes this explicit and the forms-inventory passes found real evidence of inconsistent PK/FK usage across the schema.
3. **Before modifying a form, check for parallel/near-duplicate copies** in other folders or projects (numbered folders, `New folder`, `_New`/`_2`/`Old`/`OLD` suffixes) — given the scale of copy-paste duplication documented above, a fix applied to only one copy is very likely incomplete. `FORMS_INVENTORY.md` documents many known duplicate/near-duplicate pairs.
4. **Before assuming a file is dead code, check the owning `.csproj` for `<Compile Remove>`** — several modules have substantial excluded-but-present code (notably all of `ProductionsRates\Work_Out\`).
5. **New database access should go through the existing `operations`/`*CLS` layering already used by the surrounding code**, matching whatever pattern the specific project/folder already uses (raw `operations` calls vs. EF Core `My_DbContext` vs. typed DataSet/TableAdapter) rather than introducing a fourth pattern — consistency with the immediate neighborhood matters more than solution-wide uniformity, since none currently exists.
6. **Never write a raw connection string, password, or the values found in `ReturnConnStr()`/`DBConfig.cs`/`BackupDB_CLS.cs` into a new file, commit, log, or document** — treat these as live secrets requiring rotation, not sample data.
7. **Preserve the existing error-handling shape** (`try/catch` + `MessageBox.Show` for user-facing errors, optionally `AccountModelsLib.operations.DataDictionaryLogerException(ex)` for logging) when touching a form that already uses it, rather than introducing a different exception-handling style in the same file.
