## 1) ما وجدته فى الخلفية (يحدد الخطة)

1. **المحرك كله فى `AccountModelsLib`** (متاح لـRazor بلا إضافة مراجع): `Bills_ModelsClss` (`Make_Bill_Update_SupplierAccount` بنسخة `BillOperationCLS_New/BillOperationListCLS_New`، `Edit_Bill_Update_Supplier_Account`، `Make_Bills_List_Reverse_Update_SupplierAccount`، `Edit_Bill_List_reverse_Update_Supplier_Account`، `Make_New_Invoice_No(_Reverse)`، `UpdatePurchasePrice`)، و`BillsClss` (قوائم/بحث)، و`Suppliers_AccountsCls` (`Set_Supplier_Balance_MakeBill` بمعاملات `long`)، و`sup_quantity`. أى لا حاجة لنقل كود من مشروع WinForms (بعكس شيكات أول المدة).
2. **القالب `Make_Bill_Templat` (2628 سطراً)** هو مصدر السلوك (حسابات الإجماليات والضريبة والعمولة، رصيد المورد قبل/بعد، الأزرار، الطباعة). تُنقَل قواعده لصفحة Razor واحدة كما فعلنا فى `SalesInvoicePage`.
3. **شاشة الصنف `ItemDataBill` (2646 سطراً)** أعقد من حوار المبيعات: سعر الشراء بدل البيع، وحدات/أسعار وحدات، عمولة الصنف، ضريبة الصنف، تاريخ الصلاحية، اختيار المخزن... ويلزم مكوّن جديد `AddBillItemDialog` (لا يُعاد استخدام حوار المبيعات كما هو).
4. **`UpdatePurchasePrice`** يحدّث سعر الشراء (وربما متوسط التكلفة) على `Unit_Item` عند حفظ الفاتورة؛ يجب اختبار أثره على تكلفة المبيعات.
5. **الرأس `Bills_List` مقابل `Invoices_List`:** نفس الأعمدة تقريباً (`Is_Tax_Per_Item`, `Is_InvoiceKta3y`, `IS_Make_Sarf_Item_BalanceFromInvoice`, `Supplier_BalanceSet`, `supplieraccountbefor/after`, `Load_Payment`, `Damaghat`, `PolicaNo`, `TroodContainerNo`…) مع حقول خاصة بالمشتريات: `Load_Payment` (حمولة)، `Damaghat` (دمغة)، `Second_Total`، `PolicaNo`، `TroodContainerNo`.
6. **مخاطر أكيدة من دفعة المبيعات ستتكرر هنا ويجب فحصها أولاً (م0):** (أ) دوال بمعاملات `int` لأرقام Snowflake (`Bills_Details_Id`, `Unit_id`, `Item_id` فى `Invoice_Items_Data_Struct2` بنوع `int`، وأى `(int)` فى مسارات المورد)؛ (ب) ثقافة عربية تفسد `decimal.ToString/Parse` (نستخدم `Convert.ToDecimal(x, InvariantCulture)` و`AccountCultureGuard`)؛ (ج) أرصدة مخزنة غير موثوقة → تُتحقق من الحركات؛ (د) `Enter` مع `Immediate` (تأخير 150ms)؛ (هـ) نسخة الصفحة المعاد استخدامها بين المسارات (مفتاح تبويب/نسخة بحسب `?query`)؛ (و) أعمدة `Nullable<int>` فى موديلات لأعمدة bigint.

## 6) نتائج تدقيق المحرك (م0) — مسبار `PurchProbe` على قاعدة التطوير

**يعمل كما هو (لا يحتاج تعديل):** حفظ فاتورة مشتريات نقدية (المخزون +، حركتا مورد فاتورة/دفع تتعادلان، أمر صرف نقدية تلقائى، قيد الدفع مدين مورد/دائن خزنة)؛ الفاتورة الآجلة (المخزون +، حركة مورد واحدة)؛ قراءات EF لكل جداول Bills_*/Suppliers_Accounts رغم اختلاف int/bigint فى بعض الموديلات؛ مرتجع المشتريات إذا مُرِّر له `invD` صحيح.

**عقد الصفحة (لا يحتاج تعديل محرك):** التعديل يعتمد `Item_ProcessedFlage` للسطر: `0` سطر جديد، `-1` سطر معدَّل، `100` بلا تغيير، والسطور المحذوفة تُوضَع فى `invDlst_Deleted` بعلامة `1`. (`Item_DeletedFlage` يخص المرتجع: 0 جديد، -1 معدَّل، 1 محذوف.) `Item_Expire_Date` يجب أن تملأه الصفحة دائماً. تاريخ حركة المورد يُمرَّر تاريخاً فقط.

**أخطاء المحرك المكتشفة (كلها تحتاج موافقتك قبل أى تعديل):**
1. `Bills_ModelsClss.cs` سطر ~1097 (حفظ المرتجع) و~2024 (تعديل المرتجع): يُمرَّر `invD_O.invD` (كائن واحد يضبطه المستدعى) بدل متغير الحلقة `item` إلى `SetBalanceWithExpireDate_Tash3ela_Bill` فيفشل بـ NullReference ويُبتلع الخطأ ويبقى المرتجع غير محفوظ. الإصلاح: استبدال بـ `item` (تغيير من كلمة واحدة).
2. تعديل كمية فاتورة مشتريات: `decimal Larg_Qnty = item.Larg_Qnty ?? 0 - OLD_Larg_Qnty;` أولوية المعاملات تجعلها `item.Larg_Qnty ?? (0-OLD)` فيُضاف للمخزون **الكمية الجديدة كاملة بدل الفرق** (اختبار: 2→3 زاد المخزون 3 بدل 1). نفس النمط فى `Small_Qnty` و`Qnty_Another` وفى فرع المرتجع (~1899-1960). الإصلاح: `(item.Larg_Qnty ?? 0) - OLD_Larg_Qnty`. تنبيه: قد تكون شاشة WinForms الحالية تعوّض هذا الخطأ بتمرير قيم معدَّلة — يجب فحصها قبل الإصلاح كى لا يتضاعف التصحيح.
3. التعديل غير ذرّى وتُبتلع الاستثناءات: الفشل وسط العملية يترك الرأس معدَّلاً (net 171) بدون باقى الحركات؛ و`Excp=0` تُضبط بعد Rollback فى المرتجع (~1240)؛ كتل catch لا تعيد رسالة. الإصلاح المقترح: عند الاستثناء `Excp=1` و`Msg`= رسالة الخطأ.
4. تعديل فاتورة **نقدية**: يفشل فى `Money_Transaction_BoxOrderReportCLS.Delete_Transaction_BanksBox_NewSarf_New` سطر ~4039 (SqlNullValueException) وأيضاً decimal خارج النطاق بسبب رصيد الخزنة 17 الشاذ (~1e14) فى بيانات التطوير. الحل المقترح: أنت تصحح رصيد الخزنة 17؛ وأنا أفحص سطر 4039 (عمود null غير محمى) وأعرض عليك الإصلاح.
5. اختلاف نوع الأعمدة بين الموديلات والقاعدة (Bills_List/Bills_List_Reverse: currency_id، license_id، salesman_id، banksid؛ Bills_Details_Reverse: unit_item_table_id، store_id): القراءة تعمل، ولا يلزم تغيير الآن؛ يُنصح بتوحيدها بنفس أسلوب Customer.SalesMan_Id.

**بيانات اختبار متروكة (حسب تعليمتك):** فواتير "PurchProbe م0" (نقدية وآجلة ومرتجع)، الفاتورة الآجلة 95236351976280064 عُدِّلت عدة مرات (صافى الآن 171، كمية 3، المخزون 16483 وهو أعلى من الصحيح بسبب الخطأ 2)، ورصيد Unit_item 20233 تغيّر.

### قرارات المستخدم بعد التدقيق (نُفِّذت)
- **نُفِّذ:** `Bills_ModelsClss.cs` — استبدال `invD_O.invD` بـ `item` (حفظ المرتجع) و`invD_O.invD.Id` بـ `item.Id` (تعديل المرتجع)؛ حذف `Excp = 0` بعد Rollback فى حفظ المرتجع؛ إضافة `Msg = ee.Message` فى 4 كتل catch كانت تبتلع الخطأ. اختُبر: حفظ مرتجع بدون تحايل المسبار → Excp=0، المخزون −2، حركتا مورد + قيد.
- **قرار:** خطأ فرق الكمية (`?? 0 - OLD`) لا يُمس المحرك؛ **الصفحة تحسب الفرق** وترسل قيمة الكمية = الفرق فى الأسطر ذات `Item_ProcessedFlage=-1` (أو تُحذف السطر وتُضاف سطراً جديداً). يُتحقق منه باختبار مخزون فى م1.
- **قرار:** التعديل النقدى مؤجَّل: المستخدم يصحح رصيد الخزنة 17، وأنا أفحص سطر 4039 قبل م1 لاختبار التعديل النقدى.
- **فحص سطر 4039 (تعديل نقدى):** السبب SqlNullValueException عند قراءة `Money_Transaction_Box` بـ EF: أعمدة تقبل NULL فى القاعدة وموديل الكلاس غير nullable (`customer_id, supplier_id, account_id, subaccount_id, bank_id, order_mony_id, serial, processno`) — حركة صندوق فاتورة المورد تكون فيها `customer_id` NULL مثلاً. وفى `Order_Money`: `bank_id, total_value, currency_id, order_date, transaction_type, order_no`. الحل المقترح (ينتظر موافقة): جعل هذه الخصائص `long?`/`decimal?`… أو (الأخف) تحويل أعمدة القاعدة لـ NOT NULL DEFAULT 0 — يقرره المستخدم لأن الموديل مشترك.
