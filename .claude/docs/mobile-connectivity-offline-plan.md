### ✅ التوصية: نموذج هجين (Hybrid) من ج + د

│        ▼                                                │                             │

│                     │                                   │                             │
│               SQLite مشفّر:                              │                             │
│               بيانات مرجعية + Outbox                     │                             │
└─────────────────────┼───────────────────────────────────┼─────────────────────────────┘
                      │ HTTPS + JWT                        │ HTTPS + كوكى الجلسة
                      ▼                                    ▼
┌───────────────────────── السيرفر (داخل الشركة أو سحابى) ─────────────────────────────┐
│  AccountERP.Web (نفس العملية):                                                        │
│   • Blazor Server (الشاشات Online)                                                    │
│   • /api/v1/*  (مصادقة الأجهزة + Sync Pull/Push + عمليات الشاشات Offline)              │

## 3) تصنيف العمليات

| الرمز | الفئة | المعنى | أمثلة |
|---|---|---|---|
| 🟢 **F** | Offline-capable (قراءة وكتابة) | تعمل بلا اتصال: تقرأ من النسخة المحلية وتكتب مستنداً جديداً فى الطابور، ويُرحَّل عند عودة الاتصال | فاتورة بيع، مرتجع مبيعات، سند قبض من عميل، طلبية عميل، عميل جديد، زيارة/لا بيع، جرد سيارة |
| 🔵 **R** | Offline قراءة فقط | تعرض آخر نسخة متزامنة **مع تاريخ ووقت آخر مزامنة ظاهر**، وأى إجراء كتابة يحتاج اتصالاً | قائمة العملاء والأصناف والأسعار، رصيد العميل (حتى آخر مزامنة)، فواتيرى آخر 60 يوماً، طلبياتى |
| 🔴 **O** | Online فقط | تحتاج السيرفر لحظياً: اتساق عام، تأثير على أرصدة مشتركة، صلاحيات إدارية، أو تقارير على كامل البيانات | القيود اليومية، الأرصدة الافتتاحية، الفترات المالية، الشجرة، الإهلاك، التحويل بين الخزائن، المشتريات، الشيكات، كل الإعدادات والبيانات الأساسية (إضافة/تعديل)، كشوف الحساب والتقارير، تغيير كلمة المرور، رفع الفاتورة الإلكترونية |

### قواعد حاكمة للفئة F
1. **إنشاء فقط Offline:** يمكن إنشاء مستند جديد وتعديله/حذفه **ما دام لم يُرحَّل** (مسودة محلية). تعديل أو حذف مستند مرحَّل = **Online فقط**.
2. **السيرفر هو الحَكَم:** كل قاعدة تُعاد على السيرفر عند الترحيل (رصيد، ائتمان، خصم، صلاحية، فترة مالية مفتوحة). الجهاز يتحقق مسبقاً «بحسن نية» فقط.
3. **لا رفض صامت:** المستند الذى ينجح على الجهاز ويفشل على السيرفر (مثلاً نفد الرصيد بعد بيع من جهاز آخر) يصبح **«بانتظار مراجعة»** ويظهر للمكتب وللمستخدم، ولا يُحذف — لأن البيع تم فعلاً أمام العميل.
4. **المخزون Offline:** البيع Offline يُسمح من **مخزن مُخصَّص للجهاز/المستخدم** (مخزن السيارة) فقط، لأن رصيده لا يتغير إلا من هذا الجهاز. البيع Offline من مخزن مشترك = مسموح بإعداد صريح، ويُطبَّق عليه قرار الرصيد السالب (`ERP_V1_3` §12.3) أو يُعلَّق للمراجعة.
5. **الائتمان Offline:** الرصيد المستعمل = رصيد آخر مزامنة + مستندات الجهاز غير المرحَّلة (تحفُّظ دائماً لصالح الشركة)؛ وإن تجاوزت مدة آخر مزامنة حداً (مثلاً 24 ساعة) يُمنع البيع الآجل Offline.
6. **مدة العمل Offline:** حد أقصى (مثلاً 72 ساعة) بعدها يتوقف إنشاء المستندات حتى المزامنة (الأسعار والسياسات قد تكون تغيّرت).

## 5) البنية المعمارية التفصيلية

### 5.1 طبقة الخدمات (Ports & Adapters) — قلب الحل
- **مشروع جديد `AccountERP.Contracts`** (`net10.0`، بلا Windows ولا EF): DTOs + واجهات الخدمات لكل وحدة F/R، مثل `ICustomerService`، `IItemCatalogService`، `ISalesInvoiceService`، `ICashReceiptService`، `ICustomerOrderService`، `ISyncService`، `IConnectivityService`.
- **التنفيذ المحلى `Local*`** (فى `AccountModelsLib` أو مشروع `AccountERP.Application`): يغلّف الكلاسات الحالية **كما هى** (`CustomerCLS`، محرك الفاتورة، `CashVouchersService`، `CustomerOrdersService`) — **صفر تغيير فى السلوك** للويب والديسكتوب.
- **التنفيذ البعيد `Remote*`** (فى مشروع الموبايل): `HttpClient` مكتوب يستدعى `/api/v1`.
- **غلاف `Offline*`** (Decorator فوق `Remote*`): Online → يمرر للـ API ويحدّث النسخة المحلية؛ Offline → يقرأ من SQLite ويكتب فى الطابور (للفئة F فقط)، ويرمى `OfflineNotSupportedException` للعمليات O برسالة عربية واضحة.
- **التسجيل حسب المضيف:**

| المضيف | التسجيل |
|---|---|
| `AccountERP.Web` (Blazor Server + API) | `Local*` |
| `AccountERP.MobileDesktop` على ويندوز داخل الشبكة (اختيارى) | `Local*` (كالحالى) |
| `AccountERP.MobileDesktop` على Android/iOS | `Offline*` ← `Remote*` |

- **الصفحات:** تستبدل `new CustomerCLS()` بـ `@inject ICustomerService` **فقط فى الصفحات F/R**. صفحات O لا تُمس (تُعرض من سيرفر الويب).

### 5.2 الـ API
- **المكان:** داخل `AccountERP.Web` نفسه (Minimal API تحت `/api/v1`) — نشر واحد، نفس الخدمات `Local*`، نفس الإعدادات. (بديل: مشروع منفصل `AccountERP.Api` إن أردت فصل التحجيم — قرار §10.)
- **نقاط النهاية:**
  - `POST /api/v1/auth/login` ← Access Token (JWT، 15-30 دقيقة) + Refresh Token (أيام، مربوط بالجهاز).
  - `POST /api/v1/devices/register` ← تسجيل الجهاز (يوافق عليه المدير) + تخصيص **رقم مولِّد Snowflake** + **نطاق ترقيم المستندات**.
  - `GET /api/v1/sync/pull?dataset=customers&since={token}` ← تغييرات منذ آخر مزامنة لكل مجموعة بيانات.
  - `POST /api/v1/sync/push` ← دفعة مستندات من الطابور.
  - `GET /api/v1/sync/status/{docGuid}` ← حالة مستند.
  - عمليات Online مباشرة للشاشات F عند الاتصال (مثل `GET /customers/{id}/balance` الحى).
  - `POST /api/v1/web-session` ← تحويل الـ Token إلى كوكى جلسة لعرض شاشات O داخل WebView بلا إعادة دخول (يبنى على آلية `/Auth/Persist` القائمة).
- **الأمان:** HTTPS إلزامى، JWT موقَّع، صلاحيات المستخدم نفسها (`SysConfigMenusPERMATIONS`) تُفحص على السيرفر لكل عملية، Rate limiting، تسجيل كل طلب مزامنة. **لا SQL Server مكشوف للإنترنت إطلاقاً.**
- **الوصول من الإنترنت (حسب مكان السيرفر):** سيرفر الشركة خلف Reverse Proxy (IIS/Nginx) بشهادة TLS، أو Cloudflare Tunnel بدون فتح منافذ، أو استضافة سحابية؛ داخل الشركة فقط = Wi-Fi/VPN. قرار §10.

### 5.3 العزل لكل مستخدم (شرط مسبق)
`Common.User_Id`/`Branch_Id`/… الساكنة مشتركة بين كل طلبات السيرفر. المقترح: تحويلها إلى خصائص مدعومة بـ `AsyncLocal<UserContext>` مع رجوع للقيمة الساكنة للويندوز فورم (سلوك الديسكتوب لا يتغير)، وضبطها فى بداية كل طلب API/دائرة Blazor من المستخدم المصادَق. **يحل نفس الخطر القائم الآن فى الويب.** تغيير مشترك حساس — يحتاج موافقة وتحقيقاً مستقلاً (بند 5.4).

### 5.4 النسخة المحلية على الجهاز (SQLite مشفّر)
| الجدول المحلى | المحتوى | النطاق |
|---|---|---|
| `ref_*` (عملاء، أصناف، وحدات، أسعار، قوائم أسعار، طرق دفع، مناطق، أسباب، سياسات، إعدادات) | نسخة قراءة | مقيَّدة بفرع المستخدم ومخازنه وعملائه (عملاء المندوب) — لا تُنزَّل القاعدة كلها |
| `stock_snapshot` | رصيد المخازن المخصصة للجهاز + المحجوز | مخازن الجهاز فقط |
| `customer_balance_snapshot` | رصيد العميل وحده ومتأخراته وقت المزامنة | عملاء المستخدم |
| `recent_invoices` (+ سطور) | فواتير آخر 60 يوماً للعملاء (للمرتجع المربوط) | عملاء المستخدم |
| `outbox` | `Id`، `DocGuid`، `DocType`، `Payload` JSON، `DependsOnGuid`، `Status` (مسودة/جاهز/مُرسَل/مقبول/مرفوض/بانتظار مراجعة)، `Attempts`، `LastError`، `CreatedAtDevice`، `ServerRef`، `ServerNo` | — |
| `sync_state` | آخر `token` لكل مجموعة بيانات، آخر مزامنة ناجحة | — |
| `auth_cache` | المستخدم، تجزئة PIN محلى، صلاحيات، صلاحية الـ Offline login حتى تاريخ | — |

- **التشفير:** SQLCipher (`SQLitePCLRaw.bundle_e_sqlcipher` مُشار إليه فى الحل) بمفتاح فى `SecureStorage` للجهاز.
- **تسجيل الدخول Offline:** يُسمح فقط لمستخدم دخل Online على هذا الجهاز خلال N يوماً، بـ PIN محلى؛ لا تُحفظ كلمة المرور.

## 6) محرك المزامنة

### 6.1 الصعود (Push) — مستندات الجهاز
1. كل مستند F يُنشأ محلياً بـ **`DocGuid`** (معرّف ثابت للتكرار الآمن) + **معرّف Snowflake من مولِّد الجهاز** (لا تصادم مع السيرفر) + **رقم مستند من نطاق الجهاز** (يُطبع للعميل ولا يتغير).
2. الطابور يُرسَل **بالترتيب** مع الاعتماديات (عميل جديد قبل فاتورته؛ الفاتورة قبل تحصيلها).
3. السيرفر: جدول `Sync_Inbox` بـ `DocGuid` فريد ← إن وُجد سابقاً يُعاد نفس الرد (Idempotency) ← وإلا يُنفَّذ عبر خدمات `Local*` **داخل معاملة لكل مستند** ← الرد: `Accepted(ServerId, ServerNo)` / `Rejected(سبب)` / `PendingReview(سبب)`.
4. فشل مستند يوقف تابعيه فقط، لا الطابور كله.
5. إعادة المحاولة بتباعد تصاعدى؛ المزامنة تبدأ تلقائياً عند عودة الشبكة، وعند فتح التطبيق، ودورياً، ويدوياً بزر.

### 6.2 الهبوط (Pull) — البيانات المرجعية
- **المقترح: SQL Server Change Tracking** على الجداول المرجعية (`CHANGETABLE(CHANGES …)`): يعطى المضاف/المعدَّل/المحذوف منذ رقم نسخة، **دون إضافة أعمدة للجداول القائمة** (خيار على مستوى القاعدة والجدول — يحتاج موافقة).
- البديل إن رُفض: أعمدة `Update_ServerDateTime` (غير موثوقة الضبط فى كل المسارات القديمة) أو تنزيل كامل دورى للجداول الصغيرة.
- لكل مجموعة بيانات `token`؛ أول مزامنة = تنزيل كامل مقيَّد بالنطاق، ثم دلتا.
- الحذف على السيرفر يصل كـ «حذف» للنسخة المحلية.

### 6.3 التعارضات
| الحالة | المعالجة |
|---|---|
| نفد الرصيد على السيرفر قبل ترحيل فاتورة الجهاز | `PendingReview` + تنبيه المكتب (يُعالَج بتحويل أو تسوية)، لا رفض |
| تجاوز الائتمان بسبب حركات لم يرها الجهاز | `PendingReview` |
| تغيّر السعر على السيرفر بعد آخر مزامنة | يُعتمد سعر الجهاز (ما رآه العميل) ويُعلَّم الفرق للمراجعة إن تجاوز نسبة |
| الفترة المالية أُقفلت | `Rejected` مع سبب؛ يحتاج تدخل المكتب |
| تعديل نفس البيانات المرجعية من الجهاز والمكتب | البيانات المرجعية للقراءة فقط على الجهاز (عدا العميل المبدئى) — لا تعارض |
| وقت الجهاز مختلف | يُحفظ `CreatedAtDevice` و`ReceivedAtServer`؛ تاريخ المستند = تاريخ الجهاز ضمن حد معقول وإلا `PendingReview` |

### 6.4 شاشات المزامنة (جديدة)
- **على الجهاز:** مؤشر حالة دائم (متصل/غير متصل + آخر مزامنة + عدد المستندات المعلقة)، شاشة «المستندات المعلقة» بحالاتها وأسباب الرفض.
- **فى المكتب (Razor):** «الأجهزة» (تسجيل/حظر/آخر مزامنة/رقم المولد/نطاق الترقيم)، «مستندات بانتظار المراجعة» (قبول/تعديل/رفض بسبب)، «سجل المزامنة».

## 7) الهيكلة على الكود — مثال لشاشة F
قبل:
```csharp
var customers = new CustomerCLS().GetCustomers(...);   // داخل الصفحة
```
بعد:
```csharp
@inject ICustomerService Customers
var customers = await Customers.SearchAsync(query);     // Local على الويب، Offline/Remote على الموبايل
```
- واجهات الخدمات **غير متزامنة (async)** دائماً (لأن Remote عبر الشبكة).
- DTOs بسيطة قابلة للتسلسل (JSON) — لا كيانات EF ولا `DataTable` عبر الشبكة.
- أخطاء موحَّدة: `ServiceResult<T>` بـ (نجاح، رسالة عربية، رمز) بدل نمط `ref int Excp, ref string Msg` الحالى عند حدود الخدمة فقط (الكلاسات الداخلية لا تتغير).

## 9) القاعدة الإلزامية لكل شاشة (Definition of Done) — بعد الاعتماد

كل شاشة Razor **مبنية أو جديدة** تمر بهذه البنود قبل اعتبارها منتهية:

1. **التصنيف:** تُعلَن فئتها (F / R / O) فى ملف الخطة الخاص بها، وفى الكود بخاصية مثل `[OfflineCapability(OfflineMode.Full)]` أعلى الصفحة؛ ويُضاف سطرها لجدول §4 هنا.
2. **الشاشة O:** لا تحتاج تغييراً؛ تُعرض من سيرفر الويب داخل التطبيق. يُتحقق فقط أنها تعمل داخل WebView (عرض الشاشة الصغيرة، RTL).
3. **الشاشة R:** بياناتها عبر واجهة خدمة محقونة (لا `new XCLS()` ولا `opp.db` فى الصفحة)، ومجموعة بياناتها معرَّفة فى Pull، وتعرض «آخر مزامنة» عند العمل Offline، وأزرار الكتابة معطَّلة Offline برسالة.
4. **الشاشة F:** كل ما فى R، بالإضافة إلى: المستند يحمل `DocGuid` ومعرّف Snowflake من الجهاز ورقماً من نطاقه؛ أمر Push بمعالج سيرفر يمر بخدمات `Local*`؛ تحقق مسبق على الجهاز + إعادة كل القواعد على السيرفر؛ سلوك `PendingReview` محدد؛ التعديل/الحذف بعد الترحيل Online فقط.
5. **العقود:** DTOs + واجهة async فى `AccountERP.Contracts`؛ تنفيذ `Local` (يغلّف الكلاس القائم بلا تغيير سلوك) + `Remote` + `Offline` حسب الفئة.
6. **الاختبار:**
   - الويب: نفس السلوك قبل/بعد (اختبار حى).
   - الموبايل Online: العملية تنجح عبر الـ API.
   - الموبايل Offline (وضع الطيران): الإنشاء يُحفظ فى الطابور، ثم يُرحَّل عند الاتصال، **ولا يتكرر عند إعادة الإرسال**.
   - فحص رصيد المخزون قبل/بعد (قاعدة `Unit_Item.Full_Qua`/`D_Qua`) ورصيد العميل من الحركات لكل مستند F مرحَّل.
   - حالة تعارض واحدة على الأقل تنتهى `PendingReview`.
7. **الصلاحيات:** الصلاحية نفسها تُفحص على السيرفر عند الترحيل، لا على الجهاز فقط.

### 10.1 أنماط النشر (لأن مكان القاعدة يختلف حسب العميل)
| النمط | الوصف | ملاحظات |
|---|---|---|
| **أ. الكل فى السحابة** | الويب + API + SQL Server على نفس الشبكة السحابية الخاصة | الأبسط والأسرع للموبايل. الديسكتوب بالشركة يتصل بالقاعدة عبر VPN أو اتصال مشفّر مقيَّد بعنوان IP الشركة — **لا يُفتح 1433 للإنترنت العام**. يلزم نسخ احتياطى سحابى |
| **ب. القاعدة بالشركة والويب/الـ API فى السحابة** | نفق VPN دائم (Site-to-Site) أو Cloudflare Tunnel/Azure Relay من السيرفر السحابى إلى SQL Server بالشركة | انقطاع النفق = توقف الـ API وشاشات O على الموبايل؛ **الفئة F تستمر Offline** والديسكتوب بالشركة لا يتأثر. زمن استجابة أعلى؛ تُقلَّل الاستدعاءات (Pull بالدفعات) |
| **ج. (احتياطى) الكل بالشركة** | الويب + API على سيرفر الشركة يُنشر عبر Cloudflare Tunnel أو Reverse Proxy | لعميل يرفض السحابة |

- الكود واحد لكل الأنماط؛ الفرق فى الإعداد (`appsettings.{Client}.json` على السيرفر فقط — **لا نص اتصال على الموبايل إطلاقاً**؛ الموبايل يعرف فقط عنوان الـ API).
- **تعدد العملاء على سحابة واحدة (Multi-tenant):** إن استُضيف أكثر من عميل على نفس السيرفر، يلزم تحديد قاعدة كل عميل من الـ Token (`TenantId`) — وهذا مستحيل بالحالة الساكنة الحالية (`operations.conn_str_` ساكن)؛ **المقترح للبداية: نسخة نشر مستقلة لكل عميل** (عنوان فرعى لكل عميل)، والـ Multi-tenant الحقيقى قرار لاحق بعد م6.
- التطبيق يسأل عند أول تشغيل عن **عنوان سيرفر العميل** (أو رمز QR يمسحه من شاشة «الأجهزة» فى المكتب يحمل العنوان ورمز التسجيل).

### 10.2 أثر قرار iOS من البداية
- بناء iOS يحتاج **جهاز Mac** (بناء/توقيع) + **حساب Apple Developer** + توزيع عبر TestFlight/App Store أو Apple Business Manager للتوزيع الداخلى.
- iOS يقيّد العمل فى الخلفية: المزامنة تتم عند فتح التطبيق/عودته للواجهة وعند عودة الشبكة وبـ `BGTaskScheduler` (غير مضمون التوقيت) — لذلك **زر «مزامنة الآن» ومؤشر المعلَّق إلزاميان** ويُذكَّر المستخدم قبل الإغلاق إن وُجدت مستندات معلقة.
- الطباعة الحرارية بالبلوتوث على iOS تحتاج طابعات تدعم BLE أو معتمدة MFi — تُحدَّد قائمة طابعات مدعومة قبل خطة المندوبين.
- SQLCipher وWebView وSecureStorage مدعومة على المنصتين؛ يُختبر كل بند فى §9 على Android وiOS.
