**Batch observations (General_Ledger):** see also `CLAUDE.md`'s *Solution Structure* for the two-tree situation. **Discovery gap found and corrected**: a plain `class X : Form` grep misses forms inheriting a custom base class — this project has two such chains (`Project_ControlLIB.MyForm : Form` used by the current tree's journal-entry forms, and a 2-level chain `TempComplex_DayRegistrationFrmSP : Form` → `Complex_DayRegistrationFrmSP`/`EditComplex_DayRegistrationFrmSP` in the legacy tree) — bringing the true count to **58**, not the 54 a naive scan finds. The current tree explicitly excludes several physically-present files from compilation via `<Compile Remove>` (`Profit_Loss_StatFRMNew.cs`, `Incoming_StatementByFinancialPeriod.cs`, `Incoming_StatementByDate.cs`, `Incoming_Statement.cs`) — dead code as far as the build is concerned. Heavy duplication within the legacy tree (`Master_Account_Details` vs `_Details2`, `_DetailsTarseed` vs `_DetailsTarseed2`; the class name `NewAccount_EntryFRM` is declared identically in three different files/folders) — strong evidence of copy-paste versioning via folder renaming ("New folder", "OLD" suffixes) instead of source control. Forms rarely touch SQL directly; almost all delegate to a `*_CLS` business-logic class colocated in the project. A handful of report-print forms use the older typed-DataSet/TableAdapter + RDLC pattern with commented-out `TableAdapter.Fill` calls (`MasterAccountPrintFRM`, `Master_CostCenterPrintFRM`, `ReportTest`) — these reports may not load live data. No direct `My_DbContext` usage found in any of the 58 form files. Naming: form classes suffixed `FRM`/`Frm`/`Frm_RPT`/`ListFrm`; Arabic terms transliterated directly into English identifiers (`Da2n`=دائن/credit, `Madin`=مدين/debit, `Tar7eel`=ترحيل/carry-forward, `Tarseed`=ترصيد/balance-posting, `Mezan_Morgaa`=ميزان مراجعة/trial balance) — this transliteration convention recurs across ProductionsRates and other modules too (see `CLAUDE.md`'s *Naming Conventions*).
