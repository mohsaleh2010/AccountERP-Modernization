## 1) الفكرة باختصار

المندوب = **موظف** + **مخزن متنقل** (سيارة) + **عهدة نقدية** + **خط سير** + **جهاز محمول**. كل حركة ميدانية (تحميل، بيع، تحصيل، مرتجع، تسليم طلبية، تفريغ، إقفال) تمر عبر **نفس محركات الـ ERP الحالية** (أذون المخزن، فاتورة المبيعات، المرتجع، أذون النقدية، القيود) — لا محرك محاسبى موازٍ. الجديد هو: طبقة «وردية المندوب» التى تربط الحركات ببعضها، وقواعد الرقابة (ائتمان، خصم، إرجاع، موقع)، وتطبيق محمول يعمل بلا إنترنت ويتزامن عبر API.

```
            ┌──────────── المكتب (Razor / Desktop) ────────────┐
            │ إعداد المندوبين · خطوط السير · التحميل · الإقفال │
            │ الموافقات · العمولات · التقارير                   │
            └───────────────┬──────────────────────────────────┘
                            │  خدمات AccountModelsLib (نفس المحركات)
            ┌───────────────┴──────────────────────────────────┐
            │  SalesRep Services  ──► Order_DetailsNewCls (أذون)│
            │                       ──► محرك فاتورة/مرتجع المبيعات │
            │                       ──► CashVouchersService (نقدية)│
            │                       ──► CustomerOrdersService      │
            └───────────────┬──────────────────────────────────┘
                            │  Sync API (HTTPS + Token)  [جديد]
            ┌───────────────┴──────────────────────────────────┐
            │ تطبيق المندوب (MAUI) + SQLite محلى + طابعة بلوتوث │
            └──────────────────────────────────────────────────┘
```

## 3) مبادئ التصميم (حسب أنظمة ERP الحديثة)

1. **مصدر حقيقة واحد:** المحمول لا يكتب فى القاعدة مباشرة؛ يرسل «مستندات» إلى API تُرحِّلها نفس خدمات الـ ERP. لا منطق محاسبى فى التطبيق.
2. **الوثيقة قبل الأثر (Document-driven):** كل أثر مخزنى/مالى ناتج عن مستند له رقم وحالة (مسودة → مؤكد → مُرحَّل → ملغى بعكس). لا حذف فعلى.
3. **الوردية وحدة الرقابة:** كل مستند ميدانى يحمل `Shift_Id`؛ الإقفال لا يتم إلا بعد مطابقة المخزون والنقدية، والفروق تُقيَّد تلقائياً بإذن تسوية.
4. **المتاح المحسوب لا المخزَّن:** المتاح للبيع الفورى = رصيد مخزن السيارة − المحجوز للطلبيات (نفس قرار الطلبيات 2026-09-24: حساب لا عمود).
5. **Idempotency للمزامنة:** كل مستند من الجهاز يحمل `GUID` فريداً؛ إعادة الإرسال لا تُكرِّر الأثر.
6. **الترقيم بلا تعارض Offline:** سلسلة أرقام محجوزة لكل جهاز (Number Range) أو رقم محلى + رقم رسمى عند الترحيل — قرار §9.
7. **السياسات كبيانات لا كود:** حدود الخصم والائتمان ونافذة الإرجاع وأسباب عدم البيع جداول قابلة للضبط بالفرع/الشريحة/المندوب.
8. **الاستثناء بموافقة موثَّقة:** أى تجاوز (ائتمان، خصم، مرتجع بلا فاتورة، خارج النطاق الجغرافى) = طلب موافقة (`Approval Request`) بمن وافق ومتى، ويُرفض المستند حتى الموافقة أو يُرسَل مُعلَّقاً.
9. **الالتزام بقواعد المشروع:** لا إعادة تسمية لجداول/أعمدة قائمة، لا افتراض PK، المعرّفات `bigint` بـ Snowflake (`CallSnowflakeIdGenerate`) كبقية الجداول الجديدة، أعمدة التدقيق القياسية (`User_Id`، `OperationDate`، `Insert_ServerDateTime`، `Edit_User_Id`، `EditOperationDate`، `Branch_Id`، `ProcessNo`) على كل جدول جديد، والصلاحيات عبر `SysConfigMenus`/`SysConfigMenusPERMATIONS`.

## 4) النموذج المخزنى والمالى للمندوب

### 4.1 المخازن لكل مندوب
| المخزن | التعريف | الاستخدام |
|---|---|---|
| مخزن السيارة (صالح) | `Store` بـ `IsCar=1`، `Emp_id` = المندوب، `Branch_Id` = فرعه | البيع الفورى + الطلبيات المحمَّلة + المرتجع الصالح |
| مخزن تالف السيارة **[إضافة: مخزن مستقل لا موقع داخل المخزن]** | `Store` ثانٍ بـ `IsCar=1` ونوع «تالف/حجر» (قرار §9-ق3) | المرتجع التالف/المنتهى؛ **مستبعد من البيع** ومن «المتاح» |

> السبب: النظام لا يدعم «مواقع» (Bins) داخل المخزن؛ الرصيد فى `Unit_item` لكل (صنف × مخزن). أبسط فصل صحيح محاسبياً ومخزنياً = مخزن ثانٍ.
>
> **(توافق خطة 06):** صفوف `Unit_item` للسيارة والتالف **تُنشأ عند أول تحويل** إليهما عبر محرك الحركة (خطة 01)، لا عند إضافة الصنف. وكل حركات السيارة **أذون مخزن عادية** (خطة 03)، ونوع الطرف «سيارة مندوب» يُضاف لإعداد أطراف الأذون.

### 4.2 النقدية لكل مندوب
- **صندوق عهدة المندوب:** صف `Banks` بـ `Is_Bank=0` وحساب فرعى تحت النقدية، `Branch_Id` = فرع المندوب. كل تحصيل يدخل هذا الصندوق، والتوريد = إذن تحويل نقدية منه إلى الخزينة الرئيسية/البنك.
- **[إضافة] حد النقدية بالعهدة:** سقف لما يحمله المندوب نقداً؛ تجاوزه يُنبِّه/يمنع البيع النقدى حتى التوريد (مكافحة المخاطر).
- الشيكات المحصلة تُسجَّل بمحرك الشيكات الحالى (`Checks_Memory`) على عهدة المندوب، وتُسلَّم فى الإقفال.

### 4.3 خريطة الحركات على الأذون (بعد التوافق مع خطط المخازن — خطة 06، 2026-10-08)
**القاعدة:** كل حركة مخزنية للمندوب = **إذن مخزن عادى** بنفس صفحة الأذون وخطواتها (خطة 03) ونفس المحرك (خطة 01).
- **التحويل:** بتأكيد استلام أو مباشر حسب «طريقة التحويل» العامة والصلاحية المتقدمة «تحويل مباشر بين المخازن بدون تأكيد استلام» (خطة 01 §2.7) — نفس القاعدة للمخازن.
- **المحاسبة:** النظام **جرد دورى** (قرار م-01-1)، فلا قيود مخزون ولا تكلفة مبيعات الآن. كل حركة تحفظ **لقطة تكلفة** فتُقيَّم الحركات بالقيمة، والجرد المستمر مُخطَّط لاحقاً لكل النظام (خطة 01 §2.8) والمندوب يرثه بلا تعديل.

| الحركة الميدانية | المستند (نفس أذون المخازن) | الأثر المخزنى | الأثر المحاسبى (جرد دورى) |
|---|---|---|---|
| تحميل السيارة | **إذن تحويل 1001** الرئيسى ← السيارة | − الرئيسى / + السيارة (عند التأكيد أو مباشرة) | لا قيد |
| تفريغ المتبقى | **إذن تحويل 1001 عكسى** السيارة ← الرئيسى (1006 فقط لإرجاع تحويل خاطئ كالمخازن) | − السيارة / + الرئيسى | لا قيد |
| نقل التالف للمركز | **إذن تحويل 1001** تالف السيارة ← مخزن التالف المركزى | − / + | لا قيد |
| بيع فورى | فاتورة مبيعات (مخزن = السيارة، صندوق = عهدة المندوب، `Salesman_Id`) عبر المحرك | − السيارة | الإيراد + الضريبة (`Make_EntryForInvoices`)؛ بلا تكلفة مبيعات |
| تسليم طلبية | فاتورة من الطلبية (`Customer_Order_Fulfillments`) بمخزن السيارة | − السيارة، ويقل المحجوز | كالبيع + تسوية العربون (`Customer_Order_Deposit_Applications`) |
| تحصيل | إذن استلام نقدية (`CashVouchersService`) على صندوق العهدة | — | من الصندوق / إلى العميل |
| مرتجع صالح | مرتجع مبيعات مربوط بالفاتورة، مخزن = السيارة | + السيارة **بتكلفة السطر الأصلى** (يحدّث المتوسط) | المرتجع + الضريبة / العميل |
| مرتجع تالف | مرتجع مبيعات، مخزن = تالف السيارة | + تالف السيارة بتكلفة السطر الأصلى | كالصالح |
| صرف عينات/هدايا | **إذن صرف لعميل 1002** من مخزن السيارة | − السيارة | لا قيد |
| إتلاف مركزى | **إذن صرف للهالك 1013** من مخزن التالف المركزى | − التالف | لا قيد (يظهر بقيمته فى تقرير الهالك) |
| عجز جرد السيارة | **إذن تسوية بالنقص 1008** يُنشئه الإقفال كمسودة ويعتمده المشرف | − السيارة | **تحميل المندوب (قرار م-06-3):** من حـ/ المندوب (حسابه الفرعى) إلى حـ/ إيرادات متنوعة «استرداد عجز مخزون» بقيمة لقطة تكلفة الإذن — أو مصروف بقرار المشرف |
| زيادة جرد | **إذن تسوية بالزيادة 1007** | + السيارة | لا قيد |
| عجز نقدية | إذن تسوية نقدية | — | من ذمة المندوب (حساب الموظف الفرعى) / إلى صندوق العهدة |
| زيادة نقدية | إذن تسوية نقدية | — | من صندوق العهدة / إلى إيرادات متنوعة (أو أمانات) |
| عربون | إذن استلام مربوط بالطلبية (قائم) | — | من الصندوق / إلى العميل (دائن) |

**تكلفة الإرجاع:** بـ `P_priceAvgCost` المحفوظ على سطر الفاتورة الأصلية، والمحرك يُعيد احتساب المتوسط عند الإدخال (ق6 + م-01-3).

**مستوى التكلفة (روجع 2026-10-08، خطة 01 §2.3):** المتوسط **لكل (صنف × فرع)** — مخزن السيارة ومخزن تالفها يشتركان فى متوسط فرع المندوب، فالتحميل والتفريغ ونقل التالف داخل الفرع **لا تغيّر التكلفة**، وتكلفة السطر = متوسط الفرع الحالى. **دورة المستند:** مسودة ← ترحيل ← تصحيح بمستند عكسى (خطة 01 م-01-8)؛ مستندات الجهاز تُرحَّل عند المزامنة ولا تُعدَّل بعدها.

## 6) الدورات التشغيلية (Workflows)

### 6.1 فتح الوردية والتحميل
1. المشرف/أمين المخزن يفتح «تحميل السيارة» للمندوب والتاريخ.
2. **[إضافة] اقتراح التحميل الآلى:** = (أصناف طلبيات العملاء المؤكدة المجدولة للتسليم مع هذا المندوب فى هذا اليوم − ما بالسيارة منها) + (كمية الأمان لكل صنف للبيع الفورى، من متوسط مبيعات المندوب آخر N أيام أو حد ثابت) − (رصيد السيارة الحالى المتاح). المستخدم يعدّل ثم يعتمد.
3. الاعتماد يُصدر **إذن تحويل 1001 عادياً** (الرئيسى ← السيارة) يظهر فى «تحويلات بانتظار الاستلام» كأى تحويل بين مخزنين.
   - **فتح الوردية (قرار م-06-2):** تُنشأ `SalesRep_Shifts` بحالة «مفتوحة» عند **تأكيد المندوب للاستلام** على جهازه (مستند Offline مسموح).
   - **التحويل المباشر:** إن كان مباشراً حسب الإعداد/الصلاحية تُفتح الوردية عند الإصدار.
   - **الرصيد الافتتاحى للوردية:** يُحفظ فى `SalesRep_Shift_Stock` من رصيد السيارة لحظة الفتح.
4. الجهاز يسحب: الوردية، رصيد السيارة، المحجوز، خط السير اليوم، العملاء وأرصدتهم وحدود ائتمانهم، فواتيرهم آخر 60 يوماً (للمرتجع)، قوائم الأسعار، السياسات.
5. **قاعدة:** لا بيع على الجهاز بلا وردية مفتوحة؛ وردية واحدة مفتوحة لكل مندوب.

### 6.2 زيارة العميل
`Check-in` (GPS + مقارنة بنطاق العميل) ← الإجراء: بيع فورى / تسليم طلبية / أخذ طلبية / تحصيل / مرتجع / **لا بيع (سبب إلزامى + صورة إن لزم)** ← `Check-out`. الزيارة خارج النطاق: مسموحة بعلامة ومراجعة، أو ممنوعة إلا بموافقة (سياسة).

### 6.3 البيع الفورى (Van Sales)
- الأصناف من «المتاح» فقط (رصيد السيارة − المحجوز لطلبيات غير هذا العميل).
- السعر من سلسلة الأولوية: `Customer_Price` ← قائمة العميل `Price_Type_List_ID` ← قائمة المندوب ← سعر الصنف الافتراضى.
- الخصم ≤ أقل سقف بين (المندوب، الشريحة، الصنف)؛ أعلى = طلب موافقة.
- آجل: يُفحص `رصيد العميل المحسوب من الحركات + قيمة الفاتورة ≤ حد الائتمان` و`لا فواتير متأخرة > Max_Overdue_Days`. الرصيد على الجهاز = آخر مزامنة + حركات الجهاز غير المرحَّلة (تحفُّظ).
- الضريبة: نفس قواعد المشروع — `IsInvoiceTaxInfo`/`Is_Tax_Per_Item`؛ **لا استعمال لـ `Invoice_Type` كعلامة ضريبة** (يبقى فقط لسلسلة الترقيم).
- الطباعة الحرارية + QR. **[إضافة]** للبيع لأفراد (B2C) فى مصر يلزم الإيصال الإلكترونى (ETA e-Receipt) بشروطه (تسجيل نقطة البيع/الجهاز)؛ للشركات (B2B) فاتورة إلكترونية بالمسار الحالى. قرار §9-ق10.
- **[إضافة] العروض والبضاعة المجانية:** الأعمدة `LargItemsQnty_Free`/`SmallItemsQnty_Free`/`Qnty_Free` قائمة على سطر الفاتورة؛ تُضبط بسياسة عروض (مرحلة لاحقة).

### 6.4 الطلبية المسبقة (Pre-Sales)
- تُنشأ بـ `CustomerOrdersService` الحالى (حالة مؤكدة ← حجز محسوب)، مع `Delivery_Mode`.
- فحص الائتمان والأسعار والخصم كالبيع الفورى.
- العربون: إذن استلام مربوط بالطلبية (قائم).
- **[إضافة] إشعار العميل (SMS/WhatsApp):** طابور إرسال (Outbox) يُرسَل من السيرفر، لا من الجهاز. مرحلة لاحقة.

### 6.5 تسليم الطلبية عند الباب
- قائمة «عملاء اليوم ذوو طلبيات جاهزة» من الوردية.
- زر واحد: الطلبية → فاتورة بالمتبقى (تنفيذ جزئى مسموح عبر `Customer_Order_Fulfillments`)، تسوية العربون تلقائياً (`ApplyDepositsToInvoice` — حالياً يدوى، يصبح تلقائياً هنا).
- رفض/استلام جزئى: الباقى يعود للمتاح (لأن المحجوز = المطلوب − المنفَّذ − الملغى) مع سبب، والطلبية تبقى مفتوحة أو تُلغى جزئياً بسبب.

### 6.6 المرتجع المربوط بالفاتورة
1. اختيار الفاتورة الأصلية من فواتير العميل المحمَّلة (آخر 30-60 يوماً).
2. البنود تُسحب آلياً: الكمية المباعة، السعر الصافى بعد الخصم الأصلى، الضريبة، التشغيلة، التكلفة.
3. **المسموح بإرجاعه = المباع − مجموع المرتجع سابقاً** (من `SalesRep_Invoice_Return_Links`، محسوب لا مخزَّن؛ على الجهاز = المحسوب عند المزامنة − مرتجعات الجهاز غير المرحَّلة).
4. نافذة الإرجاع (14/30 يوماً حسب السياسة)؛ خارجها = موافقة.
5. التشغيلة: يجب أن تكون ضمن تشغيلات سطر الفاتورة (`Unit_Item_ExpireDate_Id`)؛ مسح GS1-128/DataMatrix اختيارى.
6. السبب إلزامى + صورة حسب السبب + حالة (صالح ← مخزن السيارة / تالف ← مخزن التالف).
7. القيمة = الكمية × السعر الصافى الأصلى؛ التكلفة = تكلفة السطر الأصلى.
8. الحفظ عبر محرك المرتجع الحالى + صف الربط. **السيرفر يعيد التحقق من كل القواعد** عند المزامنة (لا ثقة بالجهاز).
9. **[إضافة] تسوية المديونية:** المرتجع الآجل يُخصم من رصيد العميل؛ ربطه بفاتورة محددة مفيد لتقرير أعمار الديون (يُعرض كتسوية للفاتورة الأصلية).

**المرتجع بلا فاتورة (Blind):** (ق15) مسموح بلا موافقة لمن عنده `Allow_Blind_Return`، ويُعلَّم المستند ويظهر فى تقرير مراجعة يومى للمشرف. التسعير = أدنى سعر بيع تاريخى للصنف − أعلى خصم مسموح؛ التكلفة = المتوسط الحالى.

### 6.7 الإقفال اليومى (Daily Settlement)
1. المندوب يُنهى الزيارات ويزامن كل المستندات (لا إقفال بمستندات معلَّقة على الجهاز).
2. **جرد السيارة:**
   - **المتوقع:** = `GetComputedBalance(مخزن السيارة)` من دفتر المحرك (افتتاحى الوردية + حركاتها: المحمَّل − المباع − المسلَّم + المرتجع الصالح − المفرَّغ)، لا تجميع مستقل.
   - **الفعلى:** يُدخله المندوب أو أمين المخزن.
   - **الفروق:** أذون تسوية 1008/1007 مسودة يعتمدها المشرف. عجز البضاعة يُحمَّل على المندوب بقيد ذمة بقيمة لقطة التكلفة (§4.3).
3. **مخزن التالف:** يُنقل بالكامل إلى المخزن المركزى للتالف بإذن تحويل 1001 (نفس قاعدة التأكيد/المباشر)، والإتلاف لاحقاً بإذن 1013.
4. **المتبقى:** يُفرَّغ للرئيسى بإذن تحويل 1001 عكسى (أمين المخزن يؤكد الاستلام ويسجل الفرق)، أو يبقى عهدة لليوم التالى ويصبح افتتاحى الوردية التالية — سياسة لكل مندوب.
5. **النقدية:** المتوقع لكل طريقة دفع = التحصيلات النقدية (بيع فورى + تسليم + تحصيل قديم + عربون) − ما رُدَّ نقداً فى المرتجعات؛ يُدخل المعدود؛ التوريد = إذن تحويل من صندوق العهدة للخزينة/البنك؛ الفرق → ذمة المندوب أو إيرادات (§4.3). الشيكات تُسلَّم كقائمة.
6. **تقرير الأداء المزدوج:** المنفَّذ اليوم (بيع + تسليم) مقابل الطلبيات المجمَّعة للمستقبل، والزيارات المخططة مقابل الفعلية، وأسباب عدم البيع.
7. الإقفال يقفل الوردية؛ إعادة الفتح بموافقة فقط.

## 7) التكامل المحاسبى مع ERP (القواعد المستعملة)
- **القيود تأتى من المحركات الحالية فقط:** `Make_EntryForInvoices`/`_Reverse` للبيع والمرتجع (إيراد + ضريبة)، `CashVouchersService` للنقدية وقيد تحميل عجز البضاعة على المندوب. خدمة `SalesRep` لا تكتب قيوداً بنفسها.
- **الجرد الدورى (قرار م-01-1، محسوم 2026-10-08):** لا قيود مخزون ولا تكلفة مبيعات للمندوب كبقية النظام، والتحويل بلا قيد (يحسم ق4). المخزون الختامى يشمل مخزنى السيارة والتالف تلقائياً. الجرد المستمر وقيوده وشاشة ربط حسابات المخزون مُخطَّطة لكل النظام (خطة 01 §2.8).
- **مركز التكلفة:** المندوب أو خط السير مركز تكلفة (`Cost_Center_Tree`) لتقارير ربحية المندوب — **[إضافة]** قرار §9-ق8.
- **الفروع والعملات:** كل مستندات المندوب بفرعه (`Branch_Id` = فرع المندوب/السيارة)، والعملة الأساسية؛ `Equivalent_*` كالمعتاد.
- **العمولة:** عند الاعتماد، قيد استحقاق: من مصروف عمولات المبيعات / إلى حساب المندوب (موظف) — أو تُرحَّل للمرتبات.
- **الاتزان:** يُتحقق بعد كل مرحلة أن مدين الفترة = دائنها، وأن رصيد العميل المحسوب من الحركات يطابق.

## 11) الاختبار (حسب قواعد المشروع)
لكل مرحلة، اختبار حى بالمتصفح + استعلامات قراءة:
- **رصيد المخزون قبل/بعد** (`Unit_item.Full_qua`/`D_Qua` للصف صنف×مخزن): التحميل (− رئيسى / + سيارة)، البيع (− سيارة)، المرتجع الصالح (+ سيارة)، التالف (+ تالف لا سيارة)، التفريغ، التسوية.
- **المتاح والمحجوز** على السيارة بعد طلبية/تسليم/رفض.
- **القيود:** قيد لكل فاتورة/مرتجع/إذن نقدية/تسوية، والاتزان مدين = دائن للفترة.
- **رصيد العميل من الحركات** لا من العمود المخزَّن، وحد الائتمان يرفض فعلاً.
- **المرتجع:** لا يتجاوز المسموح، بالسعر الصافى الأصلى وبالتكلفة الأصلية، ونافذة الإرجاع تعمل، والتشغيلة الخاطئة تُرفض.
- **الإقفال:** الفروق تولد الأذون الصحيحة، والوردية المقفلة ترفض أى مستند جديد.
- **المزامنة (مرحلة 7):** إعادة إرسال نفس الدفعة لا تكرر شيئاً؛ مستند بعد نفاد الرصيد يُعلَّق؛ الجهاز المحظور يُرفض.
- **الصلاحيات:** مستخدم بلا صلاحية الموافقة لا يستطيع تجاوز الحدود.

## 12) المخاطر
| الخطر | المعالجة |
|---|---|
| الحالة الساكنة `Common` على سيرفر متعدد المستخدمين | شرط قبل المرحلة 7 (عزل لكل طلب) |
| SQL مدموج بلا Parameters فى المحركات القديمة | كل مدخلات الجهاز تمر بخدمات EF/مدخلات رقمية؛ لا نصوص حرة تُدمج فى SQL |
| تكرار المعرّفات (`GetTable_Id` مع Snowflake، عيب `Money_Transaction_Box.Id` بند 1.4) | الجداول الجديدة بـ `CallSnowflakeIdGenerate` فقط؛ حل بند 1.4 قبل المرحلة 3 |
| تعارض أرصدة Offline | السيرفر حَكَم + تعليق لا رفض + تقرير مستندات معلَّقة |
| تلاعب ميدانى (موقع/أسعار/مرتجعات) | Geofence + المرتجع المربوط + سقوف + موافقات موثَّقة + صور |
| فقد الجهاز | تشفير SQLite + حظر الجهاز من المكتب + Token قصير العمر |
| تعدد نسخ الشاشات فى الديسكتوب | البناء Razor أولاً على خدمات مشتركة، والديسكتوب فورمات جديدة بجانب القديم (نهج الطلبيات) |

## 13) بنود من الدليل نُفِّذت بشكل مختلف أو أُكملت
- «موقع بضاعة صالحة/تالفة داخل السيارة» ← **مخزنان** (النظام بلا مواقع داخل المخزن).
- «حقل `Returned_Quantity` على سطر الفاتورة» ← **محسوب من جدول الربط** (لا تعديل على `Invoices_Details` ولا خطر عدم تطابق).
- **أُضيف:** إدارة الأجهزة، الموافقات الموثَّقة، حد النقدية بالعهدة، اقتراح التحميل، الترقيم Offline، Idempotency، عزل الحالة على السيرفر، الإيصال الإلكترونى B2C، مركز التكلفة للمندوب، الشيكات فى الإقفال، إشعارات عبر طابور سيرفر، اختبارات الرصيد.
- **خارج النطاق حالياً:** شاحنات التوصيل المنفصلة (مسار «توصيل لاحق عبر شاحنة») تُعامل كمندوب بوضع «تسليم فقط» بلا بيع فورى — يكفى إعداد `Sales_Mode`.
