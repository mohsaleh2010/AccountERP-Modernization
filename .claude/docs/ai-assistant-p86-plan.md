## P8.6 — إعادة الطلب الذكية وتوقع الطلب — خطة تفصيلية

كُتبت 2026-11-15 (Opus) بعد P8.9.5 (`eca5b25`). تحل محل مخطط P8.6 فى `ai-assistant-p8-plan.md`. القرارات ط1… (ط = طلب) محسومة بالخيار الموصى به؛ قرارات P8 ملزمة.

> ملاحظات قبل التنفيذ:
> - **التوقع إحصائى بلا نموذج.** النموذج يشرح بنداً واحداً عند الطلب فقط (نمط `AiAnomalyExplainer`).
> - **لا تعديل على `Unit_item.Upon_Request` ولا أى عمود قديم.** الاقتراح يُحفظ فى `AI_ReorderSuggestions`، والمخرج **مسودة** فاتورة شراء عبر `AI_Drafts` (P5) يفتحها المستخدم ويحفظها بنفسه.
> - شاشة `StoreNeedsPage` تبقى كما هى؛ الجديد تبويب/زر «اقتراح ذكى» بجانبها.
> - ويب فقط للمحرك؛ الشاشة فى SharedUI والزر مخفى فى MAUI.

### حقائق من الكود

- **الاحتياجات الحالية:** `Pages/Store/StoreNeedsPage.razor` (`/store/needs`) ← `StoreMovementReportService.GetNeeds(storeType, storeId, text, skip, take)` (`AccountModelsLib/BusinessLibShared/Store/StoreMovementReportService.cs` سطر 116): الأصناف التى رصيدها (`Full_qua × F + D_Qua` بالصغرى) ≤ حد الطلب `Unit_item.Upon_Request` (بالكبرى)، الكمية = الحد − الرصيد، التكلفة بآخر سعر شراء (`Item_Branch_Cost.Last_Purchase_Price` أو `u.P_price`). الأصناف بلا حد (0) لا تظهر — وهى الأغلبية غالباً.
- **المبيعات التاريخية:** `ai.v_sales_lines` (`item_name, qty, unit_name, unit_price, line_total…`) و`ai.v_sales_return_lines`؛ يلزم ربط الصنف/المخزن ⇒ فحص 1.
- **رصيد المخزون:** `ai.v_stock_balance`.
- **المشتريات:** `ai.v_purchases` + `ai.v_purchase_lines` (المورد الأخير، سعره، الفاصل بين أمر واستلام غير متاح ⇒ مهلة التوريد إعداد).
- **المسودات:** `Tools/AiDraftTools.cs`: `create_purchase_invoice_draft` و`create_store_order_draft` (أنواع من `Store_Order_Type_Settings`، 1016/1017 مستثناة)؛ `AI_Drafts` + `AiDraftsCLS`؛ صفحة الشراء تقبل `?aiDraft=`.
- **المهام:** `IAiScheduledJob`؛ الموجز `AiBriefAlerts`.
- **قاعدة:** اختبارات الفواتير تفحص المخزون ([CLAUDE.md] قاعدة 12) — المسودة لا تغيّر المخزون حتى يحفظها المستخدم.

### القرارات (ط)

| # | القرار | السبب |
|---|---|---|
| ط1 | الوحدة = (صنف × مخزن)؛ الطلب اليومى = صافى المبيعات − المرتجعات بالوحدة الصغرى | المخزون يُدار لكل مخزن |
| ط2 | النموذج الإحصائى: **متوسط متحرك أُسّى (Holt بلا موسمية)** على المبيعات الأسبوعية لآخر 52 أسبوعاً؛ **موسمية أسبوعية/شهرية** تُضاف فقط إن توفر ≥ 2 سنة ومعامل الموسمية دال؛ الأصناف المتقطعة (> 50% أسابيع صفر) ⇒ **Croston/SBA** | ما تفعله أنظمة ERP المتوسطة (Odoo/NetSuite)؛ قابل للشرح بلا ML |
| ط3 | نقطة إعادة الطلب = الطلب المتوقع خلال (مهلة التوريد + فترة المراجعة) + مخزون أمان (`z × σ × √(L+R)`)، z من مستوى خدمة 95% (إعداد) | المعادلة القياسية |
| ط4 | مهلة التوريد `ReorderLeadDays` (7) عامة + تخصيص اختيارى لكل مورد فى `AI_ReorderSupplierLead` | لا عمود مهلة فى النظام |
| ط5 | فترة المراجعة = 7 أيام (المهمة أسبوعية) | بسيط |
| ط6 | الكمية المقترحة = max(0, نقطة إعادة الطلب + طلب فترة المراجعة − الرصيد − الوارد المفتوح)، مقرّبة لأعلى إلى الوحدة الكبرى | لا كسور |
| ط7 | يُقارن الاقتراح بحد الطلب اليدوى `Upon_Request`؛ الفرق يُعرض («النظام يقترح 12 كرتونة؛ حدك 5») ولا يُعدَّل الحد | لا تعديل بيانات قديمة |
| ط8 | الأصناف المشمولة: نشطة، لها رصيد، بيعت ≥ 4 مرات فى آخر 26 أسبوعاً؛ الباقى «بيانات غير كافية» | تقليل الضجيج |
| ط9 | المهمة أسبوعية (الأحد 03:00) تحسب لكل المخازن وتحفظ فى `AI_ReorderSuggestions` (`Id, RunId, UnitItem_Id, Item_Id, Store_Id, Branch_Id, Method, AvgWeekly, Sigma, LeadDays, ReorderPoint, SafetyStock, OnHand, SuggestQtySmall, SuggestQtyLarge, ManualReorderLarge, LastSupplierId, LastPrice, EstCost, StockoutDate, Confidence, Status ('open'/'drafted'/'dismissed'), CreatedAt`) و`AI_ReorderRuns` | لا حساب ثقيل عند فتح الصفحة |
| ط10 | «تاريخ النفاد المتوقع» = الرصيد ÷ الطلب اليومى؛ الترتيب بالأقرب نفاداً | أوضح للمستخدم |
| ط11 | الإجراء: تحديد أسطر ⇒ «إنشاء مسودة شراء» تُجمّع حسب **آخر مورد** (مسودة لكل مورد) عبر خدمة المسودات الحالية (لا أداة محادثة)؛ أسطر بلا مورد ⇒ مسودة بلا مورد | ما يفعله Odoo (RFQ لكل مورد) |
| ط12 | «تجاهل» يضع `dismissed` حتى التشغيل القادم فقط | لا قوائم سوداء دائمة |
| ط13 | «اشرح» يرسل الحقائق (السلسلة الأسبوعية مختصرة، المعادلة، المهلة) للنموذج السريع وفقرة تمر على `Verify` | شرح بلا اختراع |
| ط14 | الصلاحية: صلاحية `StoreNeedsPage` + المخازن المسموحة للمستخدم؛ إنشاء المسودة يتطلب صلاحية فاتورة الشراء | النظام القائم |
| ط15 | تنبيه الموجز `reorder_due`: عدد الأصناف التى نفادها خلال `LeadDays` | قيمة P8.1 |
| ط16 | أداة محادثة `get_reorder_suggestions(store?, top?)` تعيد آخر تشغيل | استعمال من المحادثة |
| ط17 | الإعدادات: `ReorderEnabled` (0)، `ReorderLeadDays` (7)، `ReorderServiceLevel` (0.95)، `ReorderMinSales` (4)، `ReorderHistoryWeeks` (52)، `ReorderMaxItems` (20000) | موقوف افتراضياً |

### 1) المحرك (`Razors/AccountERP.AI/Reorder/`)

- `AiReorderModels` (AccountModelsLib، net48-safe).
- `AiForecast` (pure): `Holt(series, α, β)`, `Croston(series, α)`, `SeasonalIndex(series)`, `Sigma(residuals)`, اختيار الطريقة، `ReorderPoint`, `SuggestQty`, `StockoutDate`.
- `AiReorderSources`: سلسلة أسبوعية لكل (صنف، مخزن) بـ SQL واحد مجمّع (`GROUP BY item, store, week`)، الرصيد، آخر مورد/سعر، الوارد المفتوح (فحص 3).
- `AiReorderJob : IAiScheduledJob` + `AiReorderGateway` (قراءة، تجاهل، إنشاء مسودات، شرح) + `AiReorderExplainer`.

### 2) الواجهة

- تبويب ثانٍ فى `StoreNeedsPage`: «حد الطلب» (الحالى بلا تغيير) | «الاقتراح الذكى» (`Components/Store/SmartReorderPanel.razor`): مرشحات (مخزن، بحث، «نفاد خلال X يوم»)، جدول: الصنف، الرصيد، متوسط أسبوعى، تاريخ النفاد، الكمية المقترحة، حدك اليدوى، المورد الأخير، التكلفة، الطريقة؛ صف يفتح رسماً صغيراً للسلسلة (SVG) + «اشرح»؛ تحديد ⇒ «إنشاء مسودات شراء».
- `Settings/AiReorderTab.razor`: الإعدادات، مهل الموردين، آخر تشغيل، «تشغيل الآن».

### 3) قاعدة البيانات (جديد فقط)

`AI_ReorderRuns`, `AI_ReorderSuggestions`, `AI_ReorderSupplierLead (Supplier_Id PK, LeadDays, UpdatedBy, UpdatedAt)`، إعدادات ط17، وView `ai.v_sales_item_weekly` إن لزم (فحص 1).

### 4) الأجزاء

- **P8.6.1 — النواة الإحصائية:** النماذج + `AiForecast` + harness (سلاسل اصطناعية: ثابتة، اتجاه، متقطعة، موسمية؛ ≥ 80 فحصاً بقيم مرجعية محسوبة يدوياً).
- **P8.6.2 — المصادر والمهمة والبوابة** (fake SQL)، الجداول والإعدادات.
- **P8.6.3 — التبويب فى الاحتياجات + المسودات + الشرح** + مفاتيح `AIQ_`.
- **P8.6.4 — تبويب الإعدادات + الأداة + تنبيه الموجز + الاختبارات** م-599…م-613.

### 6) اختبارات المستخدم (م-599…م-613)

- م-599 إعادة الطلب — تفعيل الميزة و«تشغيل الآن» من التبويب.
- م-600 إعادة الطلب — تبويب «الاقتراح الذكى» فى شاشة الاحتياجات يظهر الأصناف مرتبة بأقرب نفاد.
- م-601 إعادة الطلب — صنف كثير البيع رصيده قليل يظهر بكمية مقترحة بالوحدة الكبرى.
- م-602 إعادة الطلب — عمود «حدك اليدوى» يطابق شاشة حد الطلب ولا يتغير.
- م-603 إعادة الطلب — صنف مبيعاته قليلة يظهر «بيانات غير كافية».
- م-604 إعادة الطلب — الرسم الصغير للمبيعات الأسبوعية يفتح من الصف.
- م-605 إعادة الطلب — «اشرح» يعرض فقرة بأرقام الجدول فقط.
- م-606 إعادة الطلب — تحديد أسطر من موردين مختلفين ينشئ مسودة لكل مورد.
- م-607 إعادة الطلب — فتح المسودة فى فاتورة الشراء وحفظها يزيد رصيد المخزن (فحص `Unit_Item` قبل وبعد).
- م-608 إعادة الطلب — المسودة غير المحفوظة لا تغيّر المخزون.
- م-609 إعادة الطلب — «تجاهل» يخفى السطر حتى التشغيل القادم.
- م-610 إعادة الطلب — تخصيص مهلة مورد يغيّر الكمية المقترحة.
- م-611 إعادة الطلب — مستخدم بمخزن واحد يرى مخزنه فقط.
- م-612 إعادة الطلب — سؤال المحادثة «ما الأصناف التى ستنفد هذا الأسبوع؟».
- م-613 إعادة الطلب — تنبيه الموجز بعدد الأصناف القريبة من النفاد.
