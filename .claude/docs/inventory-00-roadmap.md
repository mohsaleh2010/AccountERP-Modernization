## 2) ما وجدته فى النظام الحالى (حقائق تبنى عليها كل الخطط)

### 2.1 أذونات المخزن
- **شاشة واحدة لكل الأذون:** `Store_LIB\OrdersNew\NewLast\Order_DetailsWorkNewFrm.cs` (3759 سطراً، ترميز Windows-1256) تُفتح من 22 عنصر قائمة بنوع الإذن `StoreOrderType` (1001…1023). محرك الحفظ: `AccountModelsLib\Models\Store\CLS\Order_DetailsNewCls.cs` (4801 سطراً).
- **الجداول:** رأس `Order_Purshing` + سطور `Detailes_Purshing` + سجل الحركة الموحَّد `Detailes_Purshing_Import_Export`.
- **كل إذن له اتجاه:** `Transaction_Type` 1 = وارد (+)، 2 = منصرف (−)، والطرفان `Type_From/Id_From` و`Type_To/Id_To` (مخزن 4، عميل 2، مورد 1، قسم 20، ماكينة 23، موظف، ورشة، إنتاج 10…).
- **التحويل بين مخزنين:** إن كان الإعداد `Make_Store_Order_Sarf_Estlam_Ta7weel_Automatic_Between_Stores = 1` يُنشأ إذن مقابل تلقائياً ويتحرك الرصيدان معاً؛ وإن كان 0 (القيمة الافتراضية فى الكود) يُخصم من المرسل فقط ويحتاج إذن استلام منفصل.
- **عناصر قائمة بلا شاشة:** «إذن صرف لقسم» و«إذن إستلام من قسم» (معالج فارغ)، و«بحث أذونات صرف إلى موظف» (بلا معالج).

### 2.2 الرصيد
- `Unit_item` = صف لكل (صنف × مخزن): `Full_qua` (كبرى) / `D_Qua` (صغرى) / `Item_No` (عبوات).
- **يُكتب من أماكن كثيرة بـ SQL مباشر:** محرك الأذون (46 موضعاً)، `Requests_Cls` (46)، `Bills_ModelsClss` (44)، `Order_DetailsCls` القديم (25)، `ItemCLS` (25)، `CommonAccounts` (11)، وشاشات أصناف وأذون فى `Store_LIB` (أكثر من 40). لا توجد نقطة واحدة تضمن الرصيد.
- **سجل الحركة** `Detailes_Purshing_Import_Export` تكتب فيه الفواتير والمشتريات (`InvoiceDataSetCLS.Set_ItemTransactionFrom*`) وأذون المخزن: 6860 صفاً فى قاعدة التطوير. هذا هو الأساس الصالح لـ «الرصيد = أول المدة + الحركات».
- قاعدة التطوير شبه خالية من الأرصدة: 551 صنفاً و1398 صف `Unit_item` و**2 صف فقط برصيد غير صفرى**؛ 10 مخازن ليس بينها سيارة. الاختبار سيحتاج بيانات تجريبية.

### 2.3 التكلفة
- `Unit_item.P_priceAvgCost` (متوسط مرجَّح) و`P_Price` (آخر سعر شراء) و`StorePriceTypeEnum` (متوسط شراء / آخر شراء / متوسط بيع / آخر بيع) تُستعمل فى تسعير الأذون.
- **المتوسط يُحدَّث فقط فى «إذن استلام من مورد» (1004)** عبر `ItemCLS.ComputeUpdateP_AvgCost`. **فواتير المشتريات لا تحدّثه** (لا ظهور لـ AvgCost فى `Bills_ModelsClss`/`BillsClss`/`CommonAccounts`). أى أن المتوسط غير موثوق لمن يشترى بالفواتير.
- `ComputeUpdateP_AvgCost` يبدأ بـ `UPDATE Unit_item SET P_priceAvgCost = Item.P_priceAvgCost … WHERE P_priceAvgCost = 0` **بلا شرط على الصنف** — يمس كل الأصناف فى كل استدعاء.

### 2.4 المحاسبة
- **لا قيود مخزنية إطلاقاً:** أذون المخزن لا تنشئ قيوداً، وقيد الفاتورة (`Account_Entry_Invoice_CLS`) يقيد المبيعات والضرائب والعمولة فقط، و`Common.Account_Type_ForCOGS = 61` **معرَّف وغير مستعمل**.
- النظام فعلياً **جرد دورى (Periodic)**: المخزون يدخل الحسابات الختامية عبر `Financial_Period_Stores_Balance` (أول/آخر المدة لكل نوع مخزن: خامات، تحت التشغيل، تام) — لا تكلفة مبيعات لكل فاتورة.
- `ERP_V1_3.md` §11-§23 يصف مصفوفة قيود جرد مستمر (COGS، تسويات، WIP) — **وصف مستهدف لا يطابق الكود الحالى**.

### 2.5 الإنتاج
- «إذن استلام من الإنتاج» (1009) مع خيار «استلام بالخامات»: يقرأ مكونات الصنف (`Item_Raw_Materials`) ويُنشئ تلقائياً إذن «صرف إلى الإنتاج» (1010) للخامات ويسجل الاستهلاك فى `Item_Raw_MaterialsFor_Entage*`. **لا حساب لتكلفة المنتج التام.**
- «أوامر شغل الإنتاج» (`FrmWorkOrderList`/`FrmWorkOrderEdit` + `WorkOrderList`/`WorkOrderDetail`): هيكل جديد غير مكتمل؛ الجداول فارغة.
- إنتاج النسيج (`ProductionsRates`) نشاط مستقل (معدلات عمال، ماكينات، مطواة، تطريز) — جزء كبير منه أجور وإنتاجية لا حركة مخزن.
