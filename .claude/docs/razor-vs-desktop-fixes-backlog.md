# قائمة متابعة: إصلاحات وفروق الرازور عن الديسك توب

**الغرض:** كل إصلاح أو التفاف أو فرق مقصود عملناه فى صفحات الرازور عن سلوك الديسك توب يُسجَّل هنا، لنطبّق نفس الإصلاح على الديسك توب لاحقاً ولنُذكّر به فى المراحل المتبقية، حتى يتطابق النظامان (تعليمة المستخدم 2026-09-21).
لا يُعدَّل كود الديسك توب إلا بموافقتك على كل بند.

**العمود «أين»:** `مشترك` = الإصلاح فى كود AccountModelsLib فالديسك توب يستفيد منه أصلاً (يكفى التحقق)، `رازور فقط` = الإصلاح فى صفحة رازور والديسك توب ما زال يحتاجه.

## سابعاً: خطة معالجة علمة «غير مرحّل» الفارغة بالكود لا بقاعدة البيانات (2026-09-22، بطلبك)
**الأساس:** لا تُعدَّل البيانات القديمة. تُعالَج بجعل القراءات تتسامح مع القيمة الفارغة، وتُصلَح الصفحات كى لا تنتج فارغاً جديداً.

**نتيجة فحص القراءات (كود مشترك `AccountModelsLib/.../Account_Entry_Invoice_CLS.cs`):** ثلاث قراءات فقط تشترط `IS_Posted_Flage = 0/1` على جداول الفواتير فتتخطى الصف الفارغ:
1. `Get_EntryFor_Invoices_Reverse` (مرتجع المبيعات) سطر ~500.
2. `Get_EntryFor_Bills` (فاتورة المشتريات) سطر ~985 — هذه هى التى أسقطت ضريبة الفاتورة 1911.
3. `Get_EntryFor_Bills_Reverse` (مرتجع المشتريات) سطر ~1168.
قراءة فاتورة المبيعات (`Get_EntryFor_Invoices`) شرطها معلَّق أصلاً فلا تتأثر؛ لذلك حركة العميل سليمة. باقى مواضع العلمة تخص السندات والشيكات وغيرها ولا تمس الفواتير.

**الخطة فى الكود (تحتاج موافقتك لأنها كود مشترك):**
- **أ) الويب (Razor):** تمّ — `IS_Posted_Flage ??= 0` فى صفحة المشتريات (فاتورة ومرتجع) وصفحة المبيعات (بيع ومرتجع) وصفحة الكاشير؛ صفحة التجميل تضبطها عبر `MapInvoices`.
- **ب) القراءات المشتركة:** تغيير الشروط الثلاثة إلى `ISNULL(X.IS_Posted_Flage, 0) = <القيمة>`؛ فيُعامَل الفارغ كصفر (غير مُرحَّل) كما يفعل الأصل. تعديل سطر واحد لكل قراءة، والأثر المتوقع: أى فاتورة/مرتجع قديم فارغ العلمة يُعالَج كغير مُرحَّل عند الحفظ أو التعديل.
- **ج) الفاتورة 1911 (ناقصة حركة ضريبتها 61.60):** لا تُصلَح بتعديل قاعدة البيانات؛ يكفى فتحها فى صفحة المشتريات وحفظها (التعديل يعيد بناء حركات المورد وقد صارت العلمة 0). يُتحقَّق بعدها أن حركاتها 440 + 61.60.
- **د) اختبار:** حفظ فاتورة مبيعات ومرتجع وكاشير جديدة والتأكد أن العلمة 0؛ ثم تعديل مشتريات قديمة فارغة العلمة والتأكد من ظهور سطر الضريبة.

**الخطة للويندوز فورم:**
- الديسك توب يحفظ 0 أصلاً، فلا يحتاج تعديل حفظ.
- القراءات الثلاث فى AccountModelsLib مشتركة، فتعديل (ب) ينتقل تلقائياً للديسك توب عند بنائه بعد التعديل.
- يُراجَع أى نسخة مكررة من هذه القراءات فى مشاريع سطح المكتب القديمة (`Accounts` و`AccountsNew` و`Requests_ClsOld`): الفحص الحالى لم يجد فيها شروطاً على علمة الفواتير غير المشتركة.
- يُحدَّث ملف التعليمات ليعرف أى مطوّر أن العلمة الفارغة تُعامَل كصفر.

**تنفيذ الخطة (2026-09-22، بموافقتك):** عُدِّلت القراءات الثلاث فى `Account_Entry_Invoice_CLS.cs` (أسطر 500 و985 و1168) إلى `ISNULL(X.IS_Posted_Flage, 0) = <القيمة>`. بُنى المشروع بنجاح، وتحقق مشروع الاختبار (وضع `flagread`): الفاتورة 1911 (علمتها NULL) صارت تُقرأ بشرط 0 (صف واحد) كالفاتورة 1912 (علمتها 0). لم تُمسّ قاعدة البيانات. الديسك توب يستفيد من التعديل عند بنائه لأنه كود مشترك (التعديل مسجَّل هنا لتراجعه).
